## Adoption blocker

**R160-1 — P2 correctness/durability: unsupported same-column schemas are silently accepted.** `service/voice_store.py:32–41` compares table presence, column *names* and the format row only. Lines 43–64 then use `CREATE TABLE IF NOT EXISTS`, which cannot install missing constraints on an existing table. Types, primary keys, NOT NULL, unique indexes and foreign keys are not checked. Lines 67–69 similarly trust an existing trigger solely by name.

Concrete source-derived counterexample: replace only `catalogue_voices`' definition with `CREATE TABLE catalogue_voices(seq INTEGER, principal TEXT, id TEXT, revision INTEGER, archived INTEGER, UNIQUE(principal,id))` while retaining the other expected tables and format row `(1,)`. It passes the current inspection. On a preset registration, insertion omits `seq`, so the accepted table stores NULL instead of allocating an integer primary key. Registration can return success, yet `list` filters that voice out with `seq > 0`. A variant also missing parent uniqueness passes inspection but makes subsequent foreign-key operations invalid. Likewise, a same-named no-op immutability trigger is accepted and suppresses creation of the required abort trigger. These are unsupported layouts, not a demand to survive arbitrary hostile DB modification. The implementation explicitly promises unsupported-schema refusal, and H0's upgrade boundary is where it must enforce that promise.

Minimal fix: validate the supported table structure and required constraints/indexes/foreign keys plus trigger definitions before exposing the store, preferably within the same initialization transaction. Refuse an incompatible existing layout without repair or table replacement. Add focused temporary-DB negatives for same column names with missing PK/unique/FK and a wrong same-named trigger; assert refusal and preservation of prior rows. Existing atomic fresh installation can remain unchanged. This counterexample was established by source reasoning; no additional executable probe or test-source change was made. A new private harness, power-loss campaign or recovery edit is unnecessary to close it.

## Behavior that is sound within the reviewed boundary

Fresh catalogue DDL and its marker/triggers share existing `Core.transaction` BEGIN IMMEDIATE/commit/rollback, retaining core user_version 1. Core retains WAL/FULL and foreign keys. Partial table presence and unsupported format rows refuse. Pre-P1 initialization returns without writes; existing Core query-only and transaction fences remain. Core owns the root lock/connection, so serialized revision handling is the intended domain model; arbitrary parallel DB writers are not an exposed interface.

Registration validates full voice semantics: exact configuration/reference text, mode/origin, settings hash, engine and design lineage consistency. JSON round-trip detaches caller state and rejects NaN; versions preserve authored identity, settings and provenance and freeze verified reference hashes. Installed bundle/selector compatibility is deliberately not established by this metadata operation. Principal-scoped SQL and per-principal names isolate catalogue records. There is no asset-owner assignment parameter, loose-file registration, arbitrary path input or new dispatcher/HTTP mutation.

`Core.asset` requires DB metadata, validates its schema/ID and opens the managed file with O_NOFOLLOW; fstat checks regular file, UID, one link and size, then hashes the opened descriptor. H0 uses this actual path, not a fake validator. It does not pin a historical inode in metadata or establish decode/acoustic validity. Trusted direct asset principal takes precedence; historical artifact/job fallback requires the owner set to equal the caller alone. Ownerless/foreign records refuse. No client ownership assertion becomes authoritative here; H1 must preserve that trust boundary.

Idempotency records and mutation commit together. Principal/operation/key scope and canonical object-key encoding are retained; aliases are sorted before fingerprinting. Exact valid retries return the original detached JSON before current revision/media checks. Changed valid payload conflicts. On a new registration key, existing version conflict precedes archived/revision checks; aliases check archived then revision then collisions, whereas archive checks revision then archived. This precedence is deterministic, though H2 should document it rather than infer one universal order. Invalid schema input can fail before idempotency lookup.

Canonical names cannot become another voice's alias. Alias replacement checks all collisions before deletion; rollback preserves the prior state. Archive reserves current names, prevents active resolution/new registration, and preserves direct immutable version reads and their references. Prior aliases intentionally released by an earlier alias replacement are not reserved forever. No hard delete/asset removal occurs. UPDATE/DELETE abort triggers protect normal accidental row mutations on the supported fresh schema; they are not a security boundary against trusted code with unrestricted SQL/DDL access.

## Material H1/H2 seams, not additional H0 adoption gates

- **Real reference size:** `service/core.py:646` caps verification at 1 MiB. PCM16 mono at 24 kHz reaches that near 21.8 seconds (stereo/float/higher rates sooner). Longer otherwise valid clone references fail `foreign_media`. H1 must define bounded ingest/segment/media limits and reconcile this existing Core cap before advertising general clone ingest; do not simply remove the bound or claim the tiny fixture qualifies real references.
- **Metadata/token growth:** `voice_store.py:100` returns every version ID. Twenty voices is a row-count limit, not a byte/token bound. `versions` at line 125 first calls `get`, loading the entire version-ID history even for a one-version page. Repeated registrations also persist growing voice snapshots in idempotency results. Reference text/provenance strings have no catalogue byte budget. H1/H2 need compact summaries/detail pages, a cheap existence check for version paging and explicit metadata limits under shared contract ownership before public/agent exposure. This trusted H0 source does not meet an inferred fixed list-byte budget; r159 discloses the limitation.
- **Historical ownership fallback:** lines 143–144 refuse all ownerless-asset lookups once total artifacts exceed 1,024, even if the desired asset is in the first row; each metadata body can itself be large. This fails closed rather than leaking ownership. H1 needs direct trusted ownership on new publications and an indexed/backfilled compatibility path before claiming scalable legacy adoption. Conflicting direct and historical ownership is not cross-checked; trusted publication must prevent that state.

New alias/version/archive codes match the error enum/status map. Domain JSON-schema exceptions, missing-asset `not_found`, filesystem/internal refusal codes and resource limits still require explicit H2 translation to bounded public errors; this domain store is not an HTTP adapter.
