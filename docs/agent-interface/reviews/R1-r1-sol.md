## Blocking findings

### F1 — P1/high: failed resource-fault persistence can lose the admission/publication latch

Location: `service/dispatcher.py:131-140`, outer exception handler `:75-79`, observation handler `:159-162` (also ACK reset `:174`).

The resource exception handler attempts SQLite insertion before setting `self.resource_fault=True` or requesting termination. If that write fails, control reaches the outer handler, which only sets a mutable `quarantined` boolean. The next successful ALIVE observation recomputes that boolean from UNKNOWN/resource_fault and clears it. A transient filesystem/output violation has then vanished from both durable and in-memory authority. Fresh submission resumes; publication has no remembered resource fault either. This contradicts RESOURCE-R1's explicit claim that allocator persistence failures quarantine the writer, and is an in-scope admission failure rather than the deferred complete P1 filesystem matrix.

Reproduced against the temporary exact-SHA export with the existing E1 Runtime: in the owner-thread `prespawn` hook install `CREATE TRIGGER fail_fault BEFORE INSERT ON resource_faults BEGIN SELECT RAISE(ABORT,'fault_write_failed'); END`; submit one job; after start create its stage/output.wav with 10,000 bytes; await status.error `IntegrityError`; remove that temporary output; wait 0.5 seconds. Observed `quarantined:true` become `false`, reservation remain `executing`, phase become `observing`; a fresh key `b` was accepted as `queued`. No actual engine, external data or exploit was used. The trigger models an ordinary failed journal write without filling a real filesystem.

Required closure: set a fail-closed in-memory latch before fallible persistence, preserve it across all observation/ACK handlers, retain ownership and prohibit new admission/publication on persistence failure. Establish a conservative restart outcome if persistence of the fault itself is unavailable; do not invent successful recovery. Add a deterministic regression for this exact write-failure/transient-resource sequence.

### F2 — P2/medium: a transient violation during pending I/O never schedules termination

Location: `service/dispatcher.py:132-140`, `:159-168`, `:177-186`.

Termination is attempted only inside the immediate `admission.check()` exception handler and only when `self.pending` is empty. A violation detected while observe/prepare/start is pending sets the durable fault but leaves no pending-stop intent. If the next check succeeds, the normal state machine repeatedly observes ALIVE, marking its phase unknown because of the resource latch, without ever calling terminate. The worker's independent deadline eventually bounds the fixed executor, and publication remains refused, but the promised resource-triggered bounded termination is absent.

Reproduced separately with the existing E1 Runtime subclass delaying observe by 0.2 seconds and counting terminate calls. Once observe was pending, replace Admission.check in that disposable process with a one-shot `ValueError('resource_stage_growth')`, then delegate subsequent checks to the original. After 0.9 seconds: `stops=0`, job `running`, reservation `executing`, `quarantined:true`, phase `unknown`. This is explicitly E1 scheduling/fault evidence, not a real disk-growth or accelerator experiment.

Required closure: latch a stop obligation independently of the instantaneous scan result, service it after outstanding I/O returns (including prepare/bind/start transitions), and continue receipt/reap observation before release. Test transient pressure during pending calls, successful stop/reap, failed/unknown stop, and no publication or early release.
