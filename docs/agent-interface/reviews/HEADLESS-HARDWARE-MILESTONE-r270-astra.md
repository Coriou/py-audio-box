## Material current finding

**R270-1 — P1, fresh installed Kokoro has no supported path to its first voice. Fix before calling the packaged CPU slice usable.**

Source reproduction, not an executed runtime reproduction:

1. Start with the fresh split installation required by `service/persistent_init.py:_validate_split_database`, lines 489–494. Its fixed-row map contains no catalogue voice/version rows; every other table must be empty. A catalogue pre-populated by hand is not the fresh installation this validator accepts.
2. Activate through `service/entrypoint.py:314–322`. Configuration supplies a trusted Kokoro context and sealed bundle mapping. Creating `KokoroContexts` verifies/snapshots that context; it does not register its embedded voice version in Core.
3. `GET /v1/voices` therefore has no registered voice. Submit the configured template's valid speech request anyway: `Dispatcher._production_command` resolves it (`service/dispatcher.py:239–246`), then `Production.generate` reloads the immutable version from the catalogue (`service/production.py:68–75`). `VoiceStore.version` raises `not_found` for the absent row (`service/voice_store.py:136–140`), before speech submission.
4. There is no public preset registration/import bridge among `service/catalogue.py:VOICE_READS/PRODUCTION_OPERATIONS` or the routes installed by `service/api.py:167–183,268–272`. `voice_save` needs a successfully published prepare candidate. Installed `KokoroContexts.resolve` accepts only `speech_generate` (`service/execution_context.py:49–56`), so preparation cannot bootstrap that candidate either. Uploading WAV bytes cannot create a Kokoro preset.
5. The installed activation test bypasses this exact gap: `tests/service/test_installed_activation.py:57–59` opens Core, calls `seed.voices.register(...)`, then closes it before exercising activation. The generation admission test similarly seeds through Core. These fixtures establish downstream behavior, not a clean installed first-use journey.

Impact: even an otherwise correctly provisioned/enrolled/qualified Kokoro deployment cannot deliver its first speech through supported user interfaces from a fresh catalogue. This is an integration omission, not a failure of the reviewed ML adapters or a reason to undo their source. The reproduction depends only on ordinary empty-catalogue state, not hostile configuration or hypothetical security assumptions.

## Other integration limits that determine sequencing

- **Installed activation still stops at Kokoro/rootful Linux.** `service/install_policy.py:209–235` accepts exactly one `kokoro-cpu` profile and one bundle; `service/host_install.py:643` verifies a Kokoro manifest; the release worker installs the Kokoro lock. `worker/runtime_supervisor.py:443–473` constructs the installed supervisor with bundle mappings only, not Pocket references or Qwen registrations/inventory. `host_install.py:875–876` requires Linux root, with local rootful/no-remapping checks at 794–802. Intel macOS with OrbStack is not currently a supported installer host. Do not remove these guards and call that integration.
- **One template is not a reusable voice service.** Pocket and Qwen store one context per principal (`execution_context.py:89–160`); Pocket also binds one operation and one exact reference mapping. Qwen rejects a different saved version explicitly. For Pocket, switching prepare to generate after saving requires trusted reconfiguration; public save does not register another executable template. Both need owner-side construction from the requested owned immutable version and managed assets, plus independent supervisor mapping validation. `service/profiles.py:select` is a useful pure selector but has no production caller. Do not advertise automatic hardware selection from its existence.
- **Discovery is route-oriented rather than configured-operation readiness.** `api.py:134–165` lists all production routes, including prepare/save, even on the generation-only Kokoro installation; operation detail says implemented without giving that limitation. Noninstalled real-engine fixtures still report synthetic/no qualified engine. Installed profiles are copied from trusted configuration with an activation check, not a fresh hardware/bundle qualification. Distinguish callable route, configured capability, installed/provisioned state and actual qualification. No discovery-time ML import or download is needed to do that.
- **The control plane remains a subset.** Current CLI/MCP mirror voice reads, upload, prepare/results/save/generate, job get/cancel and artifact/byte retrieval. Jobs list, bounded wait, cursor events and explicit retry are absent from this public surface; so are alias/archive/exchange, preset registration, typed managed provisioning/profile detail, scripts/speakers/takes/assembly/export and retained acquisition bridges. Core methods and contract catalogue entries do not constitute HTTP/CLI/MCP coverage. Finish these finite PRODUCT/plan obligations before full release; UI and public STT remain deferred. Qwen VoiceDesign is also deferred, not implemented by preset/clone support.
- **Audition distinction is sound but user control is incomplete.** Prepared PCM and generated audition are separate durable outputs; the preparation performs exact PCM16 mono segment extraction, not denoise, enhancement or generic cleaning. The public `voice_prepare_request` has no audition-text field (`contracts/v1/schema.json:1194–1232`); text comes from the trusted plan. Provide explicit client-selected audition text in the eventual reusable preparation journey, retaining its exact provenance. Never save generated audition bytes as the ordinary clone reference.
- **CPU runtime budgets need a real product decision.** `Production.prepare/generate` cap dispatched work at 25 seconds; supervisor prepare refuses a remaining budget above 30 seconds (`runtime_supervisor.py:123–125`). This is a current source limit, not measured evidence that cold Pocket/Qwen will fit constrained CPU. Do not just increase a template deadline: the entire bounded path must agree. Qualify a short Kokoro baseline first; change real-engine budgets narrowly if measurements require it, leaving fixture limits intact.
- **Cancellation/restart has an explicit remaining hole.** Post-reap literal empty-directory removal is appropriate and should remain. A kill while a named conditioning file exists can still leave nonempty UNKNOWN and block restart. r248/r258/r269 do not establish recovery from every cancellation point. Qualify loading/conditioning cancellation, then address actual snapshot lifetime with concrete backend I/O or bounded owned recovery if needed; do not add a generic retained-evidence framework or silently accept nonempty state.

The retained core direction is good: authenticated HTTP, thin clients, one Core/Dispatcher owner, immutable voice versions, atomic submission/reservation, frozen execution, independent supervisor verification and oracle-controlled publication. No new P1 corruption, ownership bypass or lifecycle regression was established by this bounded inspection. Source retention is justified at that scope; clean installed first-use is not.
