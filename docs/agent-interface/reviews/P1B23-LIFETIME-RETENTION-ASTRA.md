## Selected bound and lifetime

Use a private constant `CORE_OWNERSHIP_LIMIT = 64` in `service/core.py`, with one fixed-capacity registry of ownership records. No environment variable, caller override, dynamic growth, overflow list, eviction or cap escalation. This is a new internal ownership-admission bound, not a change to T1 storage/resource accounting. The value is an engineering allowance for a one-owner default plus substantial independent-root/test headroom; it is not derived from measurements, a SQLite FD guarantee, or T1's coincidentally 64 cleanup rounds.

**A successful constructor keeps its slot until proven DB and owner closure.** Reject the constructor-only scheme: returning its slot at successful construction permits arbitrarily many ordinary close failures later, unless a second unbounded store or unsafe release is introduced. Pre-reserving a slot immediately before close has the same hole when admission fails and the caller drops the Core. One record from acquisition through closure is the smallest coherent solution.

The explicit compatibility cost is at most **64 simultaneously admitted Core lifetimes per process**, including constructing, healthy, closing, close-blocked and uncertain records. This is deliberately not a claim that arbitrary many healthy instances remain supported. Sequential healthy construction/closure is unlimited; normal single-owner behavior is unchanged. At 63 records one new distinct root can reserve; at 64 the next refuses before root mutation/owner open/SQLite connect. At capacity, no new Core is admitted even if all records are healthy. Do not quietly increase the cap to make a test pass; report any existing legitimate >64 simultaneous-Core population for parent assessment.

Each record owns at most one Core SQLite connection and one control-owner stream, plus creating PID, identical Thread object, bounded state and root identity. Thus at most 64 such connection objects, 64 owner streams and 64 retained Thread identities are introduced by this policy. Do not store primary exceptions, tracebacks, Futures, diagnostic histories or the entire Core in the record. Thread objects and SQLite objects can themselves retain graphs; SQLite has implementation-dependent descriptors/caches. **This is a cardinality bound, not RSS <= some byte count or a precise whole-process FD cap.** It does not bound arbitrary caller-owned cursors, raw SQLite connections, other services or all live threads. Ordinary active Core resources already exist; retaining them becomes explicit instead of relying on incidental references/finalizers.

Maintain the invariant `constructing + live + closing + blocked/uncertain <= 64`; no resource-bearing transition allocates a second record. A lost caller reference does not release a slot. A constructor failure that never acquired anything releases it; a successful cleanup releases it; success of construction alone does not. Reserve the record before `mkdir_durable`, owner open and DB connect, with acquisition inside an encompassing BaseException cleanup region. Preallocation/admission failure must happen before those effects. Attach each returned resource to its existing record immediately, before any subsequent fallible initialization; no allocation of a replacement cleanup record in the exception handler.

Use the normalized absolute root key for duplicate admission under the registry mutex. Before owner open, bind/check the validated directory device/inode against other reserved records to catch aliases to an existing root; do not relax existing symlink/owner checks or substitute path normalization for them. Duplicate same-root attempts fail `control_busy` without opening another owner or DB and without adding persistent records. Reservations for roots not yet created also share the normalized key. Kernel flock remains authoritative across processes and for filesystem races. A failed cross-process flock acquisition closes only its own stream; a failing stream close retains its already-reserved slot. This residual failure is bounded; it never grants ownership of another process's lock.

## Atomicity, cleanup and abandonment

One private mutex serializes reservation, duplicate-key binding, state transitions, release and maintenance admission. Use bounded/nonblocking lock acquisition with an internal busy refusal; no spin, retry or indefinite registry wait. Hold it only for fixed-size bookkeeping, except the tightly scoped pre-fork lease below. Never hold it during SQLite/owner close, filesystem initialization, user fault hooks or directory sync. Acquiring under the mutex includes the capacity check and insertion as one operation. A concurrent or nested distinct-root constructor receives its own slot or refuses; nesting cannot bypass the cap. No GIL-dependent check-then-add.

Every record is created with the process PID and `threading.current_thread()` object, not a reusable numeric thread ID. Explicit release checks PID **before mutex acquisition**, then identical Thread object before touching resources. Mark closing under the mutex; reject concurrent/reentrant close of that record. Perform DB close once per explicit call outside the mutex. Successful return sets DB-release proof and clears the record's DB reference; only then attempt owner close. Remove the registry entry/keys and free its slot only after owner close returns successfully. If bookkeeping cannot complete, retain conservatively; never free a slot while it still owns resources. A clean terminal record may be closed again as a no-op, but an old record must never remove a newer record occupying its slot: remove by exact identity/generation, not index alone.

A raising DB close, before OR after actual SQLite close, retains DB and owner. A raising owner close after successful DB close retains owner with DB proof recorded, so explicit recovery does not reclose DB. No SELECT failure, `closed` guess, base-class close, raw FD action or after-close injected knowledge substitutes for normal successful close return. This conservative contract may retain a stream whose actual close already occurred; it does not promise a lock remains held when the owner close itself released it. The safety requirement is never voluntarily release the owner while original DB release is unresolved.

Constructor cleanup preserves the original exception/traceback and adds bounded secondary diagnostics, as now. A returned Core delegates ordinary close to the same record after the existing `active is not None` refusal. A live-owner refusal keeps its slot/owner/DB intact and grants no authority to close an active job through the private record. Restrict the record recovery entry point to failed construction or a close already permitted by Core's active check; it is not a bypass for active-owner shutdown. Once a close attempt begins, the Core is terminal for normal operations: subsequent work is refused/closed-DB, never a new connection under the old slot. Only explicit cleanup continuation is allowed. Successful close can preserve the old closed DB object on Core for compatibility, but the registry must drop its owning references.

**Owning-thread explicit recovery only, no automatic retry.** While that thread is alive, a deliberate close after correction of the external/injected fault may release the record. No queue, new cleanup worker, unlimited join or special shutdown scheduler. Once that Thread terminates, no later Thread may recover its resources; retain the bounded record until process exit. No thread-ID reuse, check_same_thread=False, finalizer, registry clear, GC disable, inherited-handle close or global resource sweep. Dead-thread test cleanup must occur by normal exit of its isolated test interpreter, not by falsely cleaning the record from the parent thread.

One abandoned record permanently reduces Core capacity by one in that process. Any record also blocks maintenance as below; ordinary work on other roots may continue within remaining capacity. At exhausted capacity, further Core admission refuses. Local diagnostic should distinguish temporary capacity/busy from unresolved cleanup and state the action: close owned Cores on their creating threads; if that is impossible, restart the process. No automatic process kill/restart. Restart here means termination followed by a fresh interpreter under the existing operator lifecycle, not a fork-only child inheriting the registry. No new public UI, wire field or protocol schema.

## Maintenance admission and fork ownership

SQLite documents that a parent-open connection must neither be used nor closed in a fork child; that includes cleanup capable of changing parent-visible state. This rule was freshly checked in [SQLite's fork warning, section 2.7](https://sqlite.org/howtocorrupt.html#_carrying_an_open_database_connection_across_a_fork_). It justifies preventive admission, not attribution of V1/V2/V3 to SQLite or a particular inherited connection.

**Require the entire Core registry to be empty**, not merely no uncertain DB, and not merely no record for the maintenance root. This rejects healthy open Cores too: they are also parent-open connections. An owner-only uncertain record also refuses conservatively. Constructor-in-flight reservations refuse, including ones not yet connected. Retained records on another root are not an exception. Existing healthy active-connection fork tests therefore need compatibility assessment; they are not evidence that this retention fix caused historical native failures.

Implement the private admission seam in `core.py`, imported by `recovery.py` (which already imports Core helpers). At `_run_bounded_maintenance`, retain the Linux/single-thread refusal, then acquire an empty-registry pre-fork lease **before os.pipe and os.fork**, and before child operation/prewrite/original source writes. Hold the registry mutex from the empty check through fork so a concurrent constructor cannot slip into the gap. Reservation attempts during that lease refuse immediately. Release in the parent on successful fork and every pre-fork/pipe/fork exception; keep existing exact-child transport ownership/cleanup unchanged. Do not wrap the whole 30-second operation in that mutex.

The fork child inherits the parent's registry PID and locked mutex. **Do not unlock, clear, rebind or close the inherited registry in the child.** The admitted registry is empty. All Core registry entry points reject PID mismatch before touching the mutex, so nested Core construction/release/maintenance admission refuses there. The child proceeds only along the existing one-shot maintenance-session route, which opens its own connections, closes them in that child and uses os._exit. Structure parent-only lease release so a child exception cannot execute parent cleanup. A new interpreter imports a new empty registry normally. External/unmanaged fork with nonempty registry is unsupported and not rendered safe by this guard; PID refusal does not claim to prevent arbitrary interpreter GC on inherited objects.

This is an internal fail-closed admission check, not spawn/exec migration, at-fork cleanup or a new service role. Retained-connection poison blocks maintenance until explicit owning-thread release or process restart. An empty Core registry is only a **necessary** condition: private readers, offline handles, arbitrary sqlite3 calls and fixture transaction-context leaks remain outside its accounting. Preserve their explicit-close requirements and the separate connection inventory/qualification. Do not advertise comprehensive proof that no SQLite handle crosses any fork.

Compatibility: existing callers receive an ordinary local ValueError refusal (e.g. `b2_maintenance_core_ownership_busy`; PID mismatch separately identifies an unsupported inherited registry). Existing CLI refusal mapping remains unchanged; where it maps ValueError to exit 75, expect that existing exit rather than inventing a new code. No child exists for this refusal, so do not synthesize exit-74/73 wait receipts or a native-guard witness. Capacity failure is similarly a local ValueError with actionable diagnostic. Unrelated existing error strings, platform refusal, C1 refusal and successful empty-registry transport remain unchanged. Tests deliberately holding a clean Core across fork must establish the intended case: close it on its creating thread before a genuine maintenance positive, or assert the new pre-fork refusal for a live-owner case. Do not change an unrelated positive into a negative to obtain a green suite. Inventory exact affected nodes and propose any necessary old-test edit individually; only the double-failure amendment below is preselected here.
