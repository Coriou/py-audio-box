## Decision: one topology and one ordinary launch

Support first **local rootful Linux Docker, ordinary local named volumes, no user-namespace remapping, private container PID/cgroup namespaces and the currently recognized cgroup-v2 process associations**. The trusted host administrator launches a packaged `scripts/headless-install.py` command (installed as `speech-box`); normal operation then uses authenticated HTTP/CLI/MCP. Its Docker and `/proc` authority stays on the host. Neither long-lived container receives the Docker socket, host PID namespace, source checkout or host authority directory.

The command exposes explicit `init`, `up`, `stop`, `status` and explicit initialization completion. `up` handles ordinary registration itself. A host service may call the same `up` after host boot; Compose restart policies remain `no`, so there is no uncontrolled worker reboot with stale registration. The launcher is a finite coordinator, not another scheduler, diagnostic framework or network administration service. It must be packaged with its source dependencies and pinned configuration; no checkout is required at the destination.

Initial support does not claim macOS Docker Desktop, remote Docker, rootless/remapped Docker, native Metal or arbitrary cgroup layouts. Their host observations are not equivalent to the local Linux observations. This is a concrete first install target, not permission to simulate a Linux host on the current machine.

### Fixed role policy

Use a closed policy identifier `docker-kokoro-split-v1`, selected only by a new explicit enrollment scope `owned-kokoro-v1`. Keep `owned-synthetic` on its existing uniform-owner semantics and inspect-only activation. Do not infer policy from the caller UID, observed ownership or a failed legacy check. No user-supplied expected UID/GID map.

| Namespace | Fixed owner and mode | Access |
| --- | --- | --- |
| `/control` and `/control/core`, Core assets/internal staging/owners | 10001:10001, directories 0700; ordinary private files 0600 | Control RW; absent from worker |
| Core SQLite, WAL, SHM, `control.lock` | 10001:10001, private regular single-link files | Every original SQLite writer runs as 10001; retain Core lifetime exclusion |
| `/receipts` | 0:0, 02700 (setgid; access bits 0700) | Worker RW; absent from control |
| `p1-init.json`, intent/creation markers, `p1-enrolled.json`, `initialized`, `lane.lock`, journal and receipt-side maintenance/archive files | 0:0, 0600 | Root initializer/host and root supervisor only |
| `/ipc` | 0:10001, 0750 | Worker RW; control RO mount |
| `lifecycle.key`, `execution.key` | 0:10001, 0640 | Root and control group read; engines cannot read |
| Lifecycle/execution sockets | 0:10001, 0660 | Preserve authenticated peer checks |
| `/staging` | 0:0, 01733 | Worker RW; control RO mount |
| Per-attempt staging directory | Existing setup: UID 10001, GID equal to fresh attempt UID, 0770 | Preserve existing attempt allocation and publication policy |
| Model bundle tree at `/models/bundles/<bundle_id>` | Provisioned sealed owner 10001; dirs 0555, files 0444, no symlinks/hardlinked files | Same exact tree RO in control and worker; engines can read |

The worker remains PID1 UID 0/GID 10001, `cap_drop=ALL`, exactly `SETUID,SETGID,KILL`, no-new-privileges, network none, read-only image and finite CPU/memory/PID limits. The setgid receipts directory makes newly created journal files inherit GID 0 without an extra worker capability. Verify this policy at startup; do not silently accept arbitrary groups.

Control remains UID/GID 10001, no capabilities, read-only image, bounded tmpfs and loopback-published authenticated API. Engines keep fresh UIDs 20000..20063 and empty supplementary groups. Preserve the finite journal/UID budget; exhaustion refuses, never rotates a lane or reuses UIDs on ordinary restart. This first installer does not claim unlimited unattended operation beyond those existing limits.

Test setgid inheritance on the actual target later. Initialization creates the directory policy once, before enrollment. No per-write identity switching in the threaded supervisor, and no chown of existing journal data.

## Why merely adding a scope is insufficient

`persistent_init.roots_checked/read_file` currently require caller ownership for all roles; `initialize` constructs Core in that same process. Core requires its own UID for root/DB. `RuntimeSupervisor` requires PID1 and `Journal._load` requires supervisor ownership. Thus neither all-root nor all-10001 initialization works.

There are four further concrete traps beyond r197:

1. `recovery.offline(write=True)` opens original SQLite as its caller. Running split-owner registration as root can create root-owned WAL/SHM; a role-aware reader alone is insufficient.
2. `snapshot` runs `Reconciliation._collect`, whose asset/control/archive checks use `os.getuid()`. A privileged reader would misclassify correctly owned control assets unless the scanner receives the fixed control-role policy.
3. `register_host` calls `SupervisorRuntime` directly. The server authenticates peer **10001:10001**, while the client authenticates server **0:10001**. A root host caller is not that client. Preserve this check; perform hello in a short UID/GID 10001 child, not by allowing root peers.
4. `validate_host_topology` currently allows no added capabilities and only the four role mounts; `_mount_touches` deliberately refuses unproved storage disjointness. The real supervisor needs three capabilities, and real models/configuration/credentials require explicit extra read-only mounts. These need one closed installed-topology adapter, not permissive mount filtering.

`compose.dispatcher.yml` supplies useful role isolation but its inline initializer chowns roots on every invocation and is not the create-only installed initializer. `compose.release.yml` is still the separate 0C fixture. Neither is an installation recipe as written.

## Create-only enrollment and private readers

Add one small shared `service/install_policy.py` for closed enrollment/configuration validation and fixed role expectations. Keep default legacy function behavior unchanged. The split policy must be explicitly passed by trusted installed entrypoints and then corroborated by matching retained enrollment; it must not be selected by untrusted metadata before filesystem checks.

Use the existing four volume identities and seed/intent/enrollment scheme. Bind the new scope's canonical configuration digest to profiles, finite budget, detached production contexts, exact bundle ID/manifest/checkpoint/revision and fixed mount mapping, control and worker image digests, and policy version. A new closed record shape for this scope may add `configuration_digest` and `ownership_policy`; do not silently change the meaning of the legacy `profile_budget_digest`. Update every closed parser in the same lot. Keep existing DB table/column layouts where possible: records already carry JSON. `persistence.initialize_enrollment` must store the validated record scope instead of the hard-coded synthetic scope. The historical `p1_format=synthetic-core` is a private storage-format discriminator, not an engine qualification: retain it and document that distinction rather than migrating DDL.

For `init`, require four host-inspected distinct empty named volumes, no existing consumers, no nested/aliased roots and exact daemon/context/name/driver/creation identity. Record intent in the protected receipts root. Only at this fresh boundary may the initializer assign the fixed ownership/modes to the empty root inodes. Retain their device/inode identities before and after. Create keys, journal, locks and markers exclusively, with fd-level identity/mode checks and fsync; no replace-on-missing enrollment repair. Initialize Core in a separately spawned, permanently dropped 10001:10001 child with cleared groups and umask 077. Give that child only the validated public enrollment/configuration over a bounded private pipe; no seed, host authority or receipt write access. Parent checks successful child exit, stable role identities and exact completed DB on a private copy before writing `p1-enrolled.json` last. Never construct Core as root and chown its output afterward.

Preserve existing intent-before-create behavior. A crash between intent and file creation remains a quarantine if creation cannot be proven; do not interpret absent output as permission to recreate it. Explicit `complete` requires the exact initialization-record digest and identities. It may fill only demonstrably not-yet-attempted deterministic steps; ambiguous/partial Core construction or changed existing bytes refuse. After enrollment, no completion/reminting path. Existing uniform installations are not upgraded, even if empty.

Extend bounded no-follow readers with internal **role policy**, not an `allowed_uids` collection. Validate all path components without first erasing symlinks via `resolve`; descriptor-relative root access is preferable. Recheck dev/inode, UID/GID, mode, type, nlink, size and timestamps before/after reads. Preserve byte/time/entry limits, WAL-aware stable copy, private 0700 temporary directory, query-only SQLite on the copy, trusted-schema off and teardown error propagation. Original SQLite is never opened for read-only inspection, even with SQLite `mode=ro`.

Locks retain their existing order: control lock first, then receipt lane lock for offline inspection. Verify regular type/single link/fixed owner/mode and path-to-fd identity, and keep descriptors held until all readers/children close. Registration deliberately uses only the control lock: the live supervisor already owns lane.lock. Require a stable journal and bracketed healthy hello; do not defeat the supervisor lock. `host_state` stays advisory when owners are live, never an acceptance snapshot.

`Reconciliation` gets an internal fixed-policy read context for root-run offline scans; normal control scans still use control UID ownership. Do not change worker staging ownership into blanket control ownership or widen accepted transient files. Publication verification remains in the UID 10001 Core writer and needs no UID exception.

## Registration and launch transaction

Package the existing observer/registration logic for import by the launch command, preferably extracting it from the hyphenated script to `service/host_install.py` and leaving `scripts/p1-operator.py` as the compatible CLI adapter. Do not duplicate registration SQL in the launcher.

1. Hold a host-side per-install launch exclusion lock in the root-owned authority directory. Verify enrollment/configuration/images/bundle roots and all retained container obligations. No implicit provisioning, pulling or downloads. On fresh init, do not leave an initializer container attached to the four volumes: direct host initialization avoids an unregistered third consumer.
2. Start the final control container in a bounded **waiting** entrypoint phase, with no Core construction, DB connection, Dispatcher or HTTP listener. Start the final worker. Both actual container identities now exist, satisfying the existing live-control/live-worker requirement without a live DB owner. Do not register a placeholder and replace it with another container afterward.
3. Obtain authenticated hello through a short control-identity helper. Choose a host child permanently dropped to UID/GID 10001 with cleared groups; pass a pre-opened, validated IPC directory fd so Docker's root-only parent directories do not need relaxed permissions. Use fd-relative key/socket access in a narrowly scoped `SupervisorRuntime` helper. It uses the existing HMAC/session and SO_PEERCRED checks. Return only bounded hello, never keys. It never opens Core or accepts arbitrary operations.
4. Reuse `register_host`'s complete consumer enumeration, actual process start ticks/PID namespace/cgroup/IPC identity checks, before/after topology bracket and root-owned provenance retention. Add the installed fixed-policy checks below. Refuse quarantined hello, unknown/stale consumers, changed roots/images/configuration or interrupted maintenance.
5. Under the existing control exclusion, parent validates the complete read-only snapshot with the split policy. Retain the exact provenance first. Registration insertion is executed by a single-purpose UID/GID 10001 child, with the inherited held control lock and trusted bounded parent input. It opens existing SQLite `mode=rw`, checks unchanged installation digest and registration prestate in its transaction, inserts only the validated registration and closes durably. Parent retains lock ownership until child reap/close and rechecks DB, journal and host/hello bracket. Never drop UID process-wide in a threaded application; never hand this child a generic SQL/action interface. No root-created SQLite sidecars.
6. Publish the registration ID to the **same waiting control container** via a fixed `docker exec --user 10001:10001` helper receiving bounded nonsecret data on stdin and exclusively writing its private tmpfs activation file. This file is a launch notification, not authority. Entry point revalidates the retained enrollment, exact current hello/configuration and existing registration gate before opening Core. Its ordinary Dispatcher startup checks and second hello stay in place. Timeout means exit/refusal, not synthetic fallback. The launcher checks the final actual incarnation and startup result before reporting success.

For an identical interrupted registration, accept an existing DB row only if ID, bytes and digest are exact and the complete live bracket is revalidated. Likewise, reuse an existing provenance file only if all bytes/identities agree; never overwrite it. A worker reboot changes boot identity and requires new provenance/registration. Old records remain. A provenance-only crash is a retained obligation, not an automatic successful registration. A failed post-insert bracket leaves the row/provenance retained but publishes no activation notification.

The scope of `offline` is **Core writer exclusion**, not “every container stopped”: live waiting control and live idle supervisor are intentional for registration. Full recovery inspection/maintenance still needs its ordinary lane-lock and stopped-consumer conditions.

### Exact installed host policy, not a relaxed historical observer

Keep legacy `Docker.observe`, `host_inventory` and `validate_host_topology` behavior for synthetic records. Add a closed installed-policy branch and include its policy/configuration digest in protected host provenance. Do not simply allow arbitrary `capadd`, arbitrary mounts or caller-asserted `actual-host-inspection`.

Observe configured user, capability drop/add, no-new-privileges, read-only rootfs, network mode, restart policy, resource limits, namespace settings and exact image IDs in addition to existing identity fields. Control must be 10001:10001/no caps; worker 0:10001 with exactly the three listed caps. Reject privileged, host namespaces, extra groups, remapping and extra devices. Compare resource settings with the enrolled finite budget; no invented measured performance claim.

Four authority volumes remain exactly the same role set and mount destinations/access. Add only these separately enumerated inputs: the exact sealed model tree RO at `/models` in both containers; a checked nonsecret install config file RO in both; and a private bearer credential file RO in control only. Config and credentials are fixed-path host-owned inputs; credentials are readable by control via root:10001 0640, never by worker. No Docker secrets implementation assumptions: inspect the resulting actual bind mounts. Hash configuration/model identity; never record credential contents in topology/provenance/logs. Models remain owned 10001 so current `KokoroContexts.verify_local` succeeds; immutable modes, hash verification and host-trusted provisioning still apply.

Validate source identity, destination, owner/mode, no-follow chain and read-only flags for each allowed input; reject extra/ancestor/descendant aliases to authority volumes. Preserve `_mount_touches`' refusal for unproved **unrelated** bind/volume storage rather than adding a generic filesystem resolver in this lot. Explicitly recognize only the enrolled external input roots, after proving their exact identities and non-overlap in the supported local layout. For this narrow proof require ordinary directories/files on the same observed host filesystem mount as the volume source directories, disjoint canonical ancestry and distinct inodes; inspect `/proc/self/mountinfo` and reject intervening or nested mounts/bind aliases on any of those trees. Different devices alone and realpath alone are not proof. This intentionally refuses layouts outside that small case rather than implementing a general alias resolver. Consequently first support is a dedicated/compatible Docker host: unrelated containers with ambiguous storage may cause a clear refusal. Do not present this restriction as general Docker-host support. Tmpfs entries must be an exact bounded allowlist, not ignored arbitrary mounts.

The host launcher must keep full retained consumer coverage. Prefer restarting the same named containers on clean stops rather than recreating/removing their historical identities; unsupported upgrades or missing historical containers refuse with a concise retained-state explanation. No volume pruning or silent container removal to satisfy enumeration. Registration/owner budgets remain finite and visible.

## Restart, failure and recovery boundary

Ordinary clean `stop` closes admission, uses the f04a3a16 lifecycle stop/reap obligations, closes Core, and stops/waits the exact registered containers. It never interprets HTTP cancellation or a signal send as proof of reap. Failed/unknown shutdown keeps capacity and evidence obligations. `up` revalidates same volumes and config, starts the two final incarnations in the sequence above and registers the new boot; voices/artifacts remain in Core. If both containers are already serving coherently, return their checked status rather than registering concurrently with a live Core owner.

Control-only restart can reuse an exact still-live worker registration only when the control incarnation still matches; any changed control start identity requires the waiting-phase handshake and a new row. Worker death with nonterminal journal records remains quarantined: no lane reset, forced acknowledgement, reservation release or automatic abandonment. Healthy terminal evidence is processed through existing reconciliation/lifecycle paths after the installed gate, including retained unacknowledged terminal results; do not manufacture terminal receipts from host container exit.

For the new scope, ship read-only inspection and normal restart, **not B2 destructive maintenance**. Explicitly reject split-owner scope before the first writable connection in `plan`, `plan_abandon`, `_maintenance_session`, `_pending_prefix` and all internal maintenance entry routes. `apply` remains unavailable. Read-only inspection can describe supported retained state; unknown/pending maintenance refuses activation. This avoids a broad rewrite of B2 while preserving old synthetic recovery behavior. A future split-owner recovery writer would need its own role-separated design; it is not a prerequisite to useful fresh-install source. Document crash-quarantine and finite lane/history limits honestly.

Separate native service accounts do not eliminate these problems: a fixed engine account loses fresh-attempt isolation; retaining fresh UIDs needs a privileged launcher/reaper anyway, and the existing receipt claims specifically require PID1 namespace reap. Native Linux would need a new containment/process-death adapter; macOS additionally lacks this peer/cgroup/PID1 model. It is more implementation and qualification work, so **do not select it for this unblock**.

### Meaningful verification obligations for implementer

Test the privilege boundary, not just parser happy paths: root receipt reader versus control-owned DB/WAL/SHM; original sidecars stay UID/GID 10001 after registration; root hello fails but dropped helper succeeds; engine UID cannot obtain either key or receipts; two competing initializers/registrars and a live Core owner cannot bypass exclusion. Pure mocked UID checks alone cannot prove OS permission behavior: keep those source tests labelled, and reserve real multi-UID/peer checks for an explicitly authorized Linux test environment.

Fault points: root ownership transition, each intent/create/fsync, partial Core schema, final enrollment marker, provenance-before-registration, registration commit/close, post-commit bracket and activation notification. Reopen preserves exact bytes/identities or refuses; no rollback chown/deletion, no reminted key, no lost primary error, no leftover unreaped helper presented as success.

Negative matrix: exchanged root/inode; same inode under two roles; symlink ancestor/file; hardlinked file; wrong UID/GID/mode; WAL mutation or teardown failure; wrong scope/profile/budget/context/bundle/image; actual worker boot changed between hellos; control recreated between registration and activation; extra capability/mount/device/group; model/secret alias; rootless/remote/unknown namespace; unknown stopped consumer; pending recovery; nonterminal journal; exhausted budgets. Assert failure occurs before public listener/dispatch and before any unauthorized original write.

Restart positives: clean terminal job plus saved voice/artifact survives; exact still-live worker can be revalidated; new worker boot gets a new retained registration; terminal proposal/ack and cancellation retain existing publication/reap rules. Legacy synthetic initialization, offline inspection, B2 rejection boundaries and enrolled inspect-only behavior stay covered without a sprawling historical campaign.
