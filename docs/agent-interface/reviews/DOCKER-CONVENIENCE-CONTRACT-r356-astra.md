## Chosen product and trust boundary

Implement explicit launch policy **`installed-daemon-volumes-v1`**, selected by a trusted packaged command, never inferred from disk metadata or public request fields. Retain the fixed Kokoro split UID/file ownership policy and frozen model/profile/configuration; distinguish launch policy from execution identity. Do not rewrite already enrolled installations or convert their historical evidence. New installation only.

First supported targets for qualification: ordinary Intel Mac CLI using its local Docker Desktop or OrbStack rootful Linux/amd64 daemon, and ordinary CLI on a Linux/amd64 rootful Docker host. Accept the local Unix socket selected through an explicit Docker context, including the desktop socket-forwarding endpoint; do not require `/var/run/docker.sock` on the client. Freeze the resolved endpoint and daemon ID for the operation and recheck them. Ignore changing ambient DOCKER_HOST/context overrides once selected. Brand names neither qualify nor forbid the new policy: actual rootful/no-remapping, cgroup-v2, fixed-UID, mount and process prerequisites decide admission. Product/version combinations remain candidates until actually tested.

Trusted: operator, client package, Docker daemon and its administrator, VM/kernel, pinned helper/control images and worker supervisor. A daemon administrator can read secrets, replace volumes and impersonate containers; this policy does not defend against that administrator. Untrusted: public clients, request text/media and UID20000+ engine children. Public credentials authorize existing HTTP operations, never installer authority. The supervisor remains trusted; arbitrary root-supervisor compromise is outside the existing isolation claim too.

Unsupported in this lane: remote TCP/TLS/SSH Docker contexts (even administratively trusted), rootless/userns-remapped daemons, non-Linux or non-amd64 engines, custom volume drivers/options, NFS/CIFS/bind-backed named volumes, shared Mac folders as persistent service storage, privileged/shared-host PID layouts, arbitrary preexisting volume adoption, VM reset/backup restoration and automatic repair/migration. Apple Silicon emulation is not qualified by Intel support. Docker CPU does not expose native Metal. CUDA and native Metal remain mandatory later compatible release rows; no backend or voice substitution is introduced.

## Minimal storage and helper contract

Use eight distinct ordinary named volumes: existing control, receipts, staging, IPC; plus authority, models, configuration and credential. The last three replace host bind inputs. Authority is on the control/administration side of the boundary but **is not the UID10001-writable control volume**. Neither long-lived runtime mounts it. A directory within `/control` owned by UID10001 cannot be launch authority.

Runtime topology remains exact:

- Control: `/control` RW; `/ipc`, `/staging`, `/models`, configuration and credential RO. UID/GID 10001, all capabilities dropped, authenticated public API on loopback only.
- Worker: `/receipts`, `/ipc`, `/staging` RW; models/configuration RO. No control/Core, credential or authority mount. Root:GID10001 supervisor with only SETUID, SETGID, KILL; network none; engine children retain existing distinct UID20000+ boundaries.
- Both retain private PID/IPC/cgroup namespaces, read-only rootfs, no-new-privileges, bounded tmpfs/memory/swap/CPU/PIDs, restart=no, pinned entrypoint/image and pull=never. No Docker init wrapper between worker supervisor and PID1.

Mount configuration and credential at separate fixed directories, e.g. `/etc/speech-box/config/install.json` and `/etc/speech-box/credentials/control.key`; update only the new-policy entrypoints. Named volumes mount directories, not synthetic host file paths. Disable Docker volume copy-up. No subpath feature or VM Mountpoint bind is needed for this Kokoro lane. Pocket reference-subdirectory mounting is out of scope.

One helper implementation has fixed install/init/up/status/stop phases. Each invocation is finite, networkless, with private namespaces, read-only rootfs, bounded resources and only the exact volumes needed by that phase. No Docker socket, host PID, host root, devices, privileged flag or SYS_ADMIN. Its root identity is deliberate initialization/maintenance authority over these volumes only. Initialization may require CHOWN/FOWNER/DAC_OVERRIDE plus SETUID/SETGID/KILL for existing synchronous child management; enumerate and test this exact set, drop ownership-changing capabilities for later phases. DAC override is confined to this trusted helper and its narrow mounts, never added to runtime workers. No arbitrary shell, path, SQL or command arguments cross its private phase protocol.

The client executes Docker create/inspect/start/TERM through its already authorized local daemon connection. The helper holds the actual nonblocking volume launch lock throughout each transaction, including client Docker actions and final checks. Implement a bounded attached stdin/stdout phase exchange: helper persists intent, client performs the one prescribed action, returns its exact inspected result, helper validates and advances. Frames bind operation nonce/phase and retained IDs; reject replay/out-of-order/extra fields. This is an internal finite installer handshake, not a generic command bus or new scheduler. Daemon observations are trusted-client input corroborated against helper-local files, not signed proof against the administrator. Never release/reacquire the lock between create, register and notify.

Client disappearance/timeout must leave durable incomplete intent and refuse activation; lock release after helper death is not completion. A new invocation detects pending state and refuses except the existing exact safe initialization-completion case. Never infer missing container IDs from labels/names. Persist an exclusive creation intent before create and exact returned IDs before start. Retain unexpected partial state; no automatic rollback, replacement, rm/prune or force-stop. Normal finite helper exit is expected; no hidden operational cleanup is needed for correctness. Known terminal helper containers are recorded as such, not silently treated as unknown consumers or unlimited ignored containers; use a finite bound and an explicit refusal when exhausted.

## Runtime activation without host `/proc` fiction

`host_install._proc_observation` currently walks VM-host cgroups and `/proc/<Docker State.Pid>/root/ipc`. Neither the Mac nor an ordinary helper can do that. Do not call it with fabricated data, translate a namespace PID into a host PID, or retain the `actual-host-inspection` label. Add one closed evidence variant for daemon-volume activation, selected only by the new trusted policy, and route its actual consumers through explicit validators. Strict host records remain unchanged and cannot accept the new projection by dropping required fields.

The replacement proves what is needed through three sources:

- **Trusted Docker inspection:** exact daemon, retained container IDs, image/entrypoint, mounts/RO flags, security/resources and private namespaces; StartedAt/running/restart state bracketed around registration and readiness. Inspect policy disallows namespace sharing, extra mounts and wrapper init. Docker State.Pid may be recorded diagnostically but is not locally dereferenced.
- **Container-local facts:** control already enforces `local_incarnation()` at PID1 and reads its own PID namespace/start ticks. Worker `RuntimeSupervisor.__init__` already requires PID1; its reaper uses `waitpid(-1)` until ECHILD before terminal persistence. Extend only a bounded private startup observation if needed to bind worker-local incarnation, fixed UID/capability state and mounted role identities to the running pinned supervisor. A Docker-exec reader is not PID1 and cannot attest that it owns children; it may read `/proc/1` and compare to the supervisor's authenticated response. Never assert that helper PID1 is worker PID1. Namespace inode/start values describe their own namespace and current kernel, not a universal host identity.
- **Existing authenticated lifecycle:** UID/GID peer checks plus nonce/HMAC session bind hello to the shared IPC key, lane and new boot. Cross-PID-namespace SO_PEERCRED PID may be unmapped/zero; existing transport compares UID/GID, and must not grow an invented host-PID equality check. An untrusted engine cannot access the key/receipts or act as the root supervisor. The trusted daemon establishes which exact container has that IPC volume. This is not cryptographic container attestation against the daemon or a compromised trusted control process.

Preserve launch order: control waiting factory with no active Core owner/public listener; final worker PID1; healthy authenticated hello and exact images/mounts/volume identities; registration under Core exclusion using the dropped writer; durable private provenance; notify the same retained control ID with its current local incarnation; control validates registration/configuration/lane/boot before owner activation and again after acquiring Core; client/helper bracket readiness against the same container incarnation and hello. Keep notification/provenance distinct from public claims. Success is returned only after the helper's final identity checks and successful finite exit; EOF/timeout/partial output is not ready.

Use existing attempt Authority, frozen inputs, worker journal, ACK/reap and publication/import fences. A healthy container, authenticated hello or new observation record never proves an attempt was reaped. Only the existing PID1-owned engine-tree lifecycle supports that receipt; control still validates terminal history before publication/capacity release. No host-process enumeration is required to infer that ownership when the worker is actually namespace PID1, creates the engine tree, lacks escape capabilities and the daemon/kernel are trusted. Those runtime premises need real qualification.

Stop remains TERM control, bounded clean owner drain/exit, clean journal/ACK/publication checks, TERM worker, bounded clean exit and stopped-history validation. No docker-stop KILL escalation. Restart reuses retained exact container IDs, verifies historical clean state and registers the new observed incarnation/boot. Missing/recreated IDs, worker boot change without corresponding restart, pending creation/registration, unknown/unreaped history, dirty exit or unacknowledged/partial publication refuse and retain. Do not demand globally unique PID-namespace inode numbers across historical restarts; bind current local observation to daemon incarnation and authenticated boot instead. Historical evidence stays immutable.
