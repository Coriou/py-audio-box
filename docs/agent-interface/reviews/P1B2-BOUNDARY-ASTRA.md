## 1. Actual call paths and the fence decision

`Core.__init__` obtains `control.lock`, opens SQLite, sets WAL/FULL/foreign keys, validates/creates the base schema and then calls `persistence.initialize(db, fresh=...)` at `service/core.py:137`. It does **not** call recovery, publish, start a worker, construct ResourceStore, or reconcile. Thus a refusal inside the existing initializer occurs before a usable Core returns, including `Core(..., historical_local=True)`. It occurs after SQLite open/PRAGMAs: this is a mutation-authority fence, **not** a source-byte-preserving inspection path. Offline inspect must continue using B1's private WAL-aware copy.

Both `Core._publish` and `Core._commit_publication` already carry `@persistence.storage_session` (`core.py:368`, `443`). Extend this existing wrapper to perform a bounded B2 publication check **before invoking either wrapped method**, before `_verified`, temporary creation/link/unlink, and before `_commit_publication`'s terminal fast return. Check pending Core recovery and exact retired job/publication identity. Put queries/validation in persistence; no decorator relocation, Core callback, constructor flag or public recovery override is necessary. `_publication_barrier` is a private subordinate helper, not an independently supported publication entrypoint.

`Core.reconcile/start/finish` explicitly require `historical_local=True`. Historical reconciliation can call `_commit_publication`, so constructor refusal alone is insufficient after recovery completes. Permanent retirement checked in the wrapper closes that path. Preserve non-enrolled historical fixtures/behavior when B2 state is absent. Enrolled direct historical execution is **not** the shipped persistent path and cannot substitute local owner-lock inference for supervisor death. B2 must reject such populations when their reservation/dispatch/provenance is incoherent, rather than recovering or migrating them. Do not make arbitrary raw SQLite writes, calling unwrapped Python methods, or a malicious administrator part of the supported API/security claim.

`Dispatcher._run` currently calls enrollment_gate only with explicit registration, then Core, Admission/DispatchStore constructors, and A2 reconciliation. The enrolled-default branch still runs those constructors/scans, although `_tick`, submit, cancel and replace remain activation-closed. Therefore B2 must gate **both** persistent-option and enrolled-default startup before these mutable steps. Merely adding `_tick` checks is too late. Retain the existing C1 activation closure after successful B2 validation.

`RuntimeSupervisor.__init__` constructs Journal before launching its watchdog; `serve` later unlinks/binds sockets. Journal acquires `lane.lock` before reading its file. Check receipt-side maintenance state under that lock, before journal loading/boot generation/listening. Missing/malformed/incomplete maintenance state on a B2-marked installation refuses; no catch-and-create journal. Non-enrolled workers with no B2 state retain existing behavior. RuntimeSupervisor's maintenance-only hello extension can expose a bounded completed recovery ID/lane/certificate digest; it is not death evidence or a public activation command.

### Cross-volume startup protocol (no new mounts or shared authority store)

Use the existing receipts maintenance fence and Core recovery record; normal control has IPC, not a receipts mount. Before constructing an enrolled Core, Dispatcher does a bounded source-preserving enrollment/B2 read and obtains authenticated worker hello. On a B2 installation it requires the exact completed receipt-side recovery certificate to match the Core completion record and lane. A refused/unavailable worker or mismatch refuses startup before Core/Admission/A2. This also applies without `persistent_registration`; omitting the option is not a bypass. Existing explicit registration remains necessary for the persistent installed start path. The preliminary read is not locking authority: repeat Core-side validation under `control.lock` in persistence.initialize and recheck the hello binding before mutable startup. Offline maintenance takes both locks, so it cannot interleave with a live Core owner.

Write the **receipt-side pending fence first**, holding both existing locks and after all containers are stopped/proved. Then commit the Core pending record, before changing any journal or resource authority. A crash with only the receipt fence blocks worker startup and hence enrolled Dispatcher startup through the hello requirement; ordinary historical Core has no B2 DB pending state yet, but no authority has been changed. A crash with both pending blocks both constructors. A Core-pending/receipt-absent state is invalid, never normal startup permission. Missing/tampered evidence is not a fresh installation.

After journal replacement and Core resolution/epoch commit, Core contains a completion certificate while the receipt fence remains pending. Dispatcher still refuses because the worker cannot hello. Finally publish the receipt completion certificate, bound to the already durable Core certificate and new journal lane. Now both are complete, worker may boot, and control still requires fresh registration/current boot. There is no cross-volume atomicity claim. Direct Core on the Core-complete/receipt-pending side cannot publish retired output because the wrapper permanently rejects it; it is not a supported cross-volume persistent launcher. Do not claim that the DB-only initializer can read or prove the other volume. No mandatory public activation or new general launcher is introduced.

Core initialization must reject pending/partial B2 schemas/records rather than add missing rows. Normal constructors do not install B2 schema. Add it atomically only in explicit offline B2 planning after validating the coherent enrolled B1 predecessor. Preserve pre-B2 databases and B1 initialization completion checks: B2 tables are an optional **complete** extension, not unconditional additions to `COLUMNS` that suddenly make every B1 initialization require them. Use separate `B2_COLUMNS` and explicit all-or-none validation.

## 2. Freeze these finite records and interfaces in B2.1

Keep public 1.3.0, Core user_version 1, R1 protocol 2, private P1 revision 1. No general migration or another authority DB. Suggested exact extension (freeze these names/column orders for implementation):

| Table | Exact columns / purpose |
| --- | --- |
| `p1_b2_format` | `id revision`; exactly `(1,1)`, installed with the whole extension |
| `p1_abandon_plans` | `id record digest`; immutable B2 plans, distinct from B1 `apply_available=false` plans |
| `p1_recoveries` | `id plan_id record digest`; immutable accepted intent, prestate/proof, fixed new lane and new epoch, expected poststate description |
| `p1_recovery_steps` | `recovery_id step record digest`; unique `(recovery_id,step)`, append-only durable receipts, including Core completion |
| `dispatch_resolutions` | `dispatch_seq recovery_id record digest`; unique `(dispatch_seq,recovery_id)`, typed FK to original dispatch and recovery |
| `p1_retired_publications` | `job_id recovery_id record digest`; exact publication/attempt/binding digest and retirement, retaining publications/work rows |
| `p1_integrity_resolutions` | `object_id recovery_id record digest`; exact original diagnostic identity/reason/content digest, decision and continuing availability status |

Use PK/FK/uniqueness constraints, exact schema validation and bounded closed JSON validators. `record,digest` are not permission for arbitrary nested data. Validators reject unknown fields, booleans masquerading as integers, nonfinite times, unknown enums, duplicate IDs, missing references and oversized aggregates before materialization. Existing 2,048 row/entry, 16 MiB aggregate, finite SQL/filesystem deadlines and journal 64-record/1 MiB limits remain ceilings; new history consumes them. Do not enlarge ceilings to make fixtures pass. A full audit history may block further maintenance; do not evict it.

Freeze B2 plan record keys: `id deployment_id revision policy source_digest observation_digest proof_digest affected prior_epoch new_epoch old_lane new_lane journal_state journal_digest budget_before budget_after diagnostic_decisions count bytes created expires`. `revision=1`, fixed policy `abandon-uncertain-synthetic-v1`, TTL <=300 seconds for initial acceptance. `affected` has typed `jobs dispatches publications reservations` lists; include every queued/executing reservation and every old unresolved dispatch, plus exact terminal records retained as evidence. Record per-job action (`retain-terminal`, `fail`, `cancel-requested`, `cancel-never-started`) in the accepted recovery's closed action records. No wildcard/path input. B1 plans remain readable, history-bound and **not applicable**; never reinterpret their unavailable flag as approval.

Accepted recovery records bind the complete plan/digest, exact source observation, death proof and its provenance, before-image digests/canonical rows for the bounded mutation set, original monitor/faults/high-water/demands, action records, diagnostic decisions, chosen lane/epoch, archive identity and expected step outputs. Define closed record schemas per step, not a general patch language. Epoch identity lives in this history; do not pretend `resource_monitor` already has an epoch column. First epoch links to the enrolled deployment; later epochs link to the previous completed recovery certificate. Both old and new budget values are explicit, finite and configuration-bound.

Private seams, implemented in existing files:

- Journal fixed archive/rotation helpers: operate under the existing journal lock, reuse its durable file write/replace/directory-sync path, and expose no generic path deletion/copy operation. Acquiring a lock is never death proof.

Receipt files use derived managed names, not caller paths: persistent `p1-maintenance.json` bound to deployment/recovery/plan/proof/old/new lane and step; recovery-specific archive directory with original journal bytes (or explicit missing status), digest manifest and immutable completion certificate. Control recovery archives must be in a specifically recognized, bounded private namespace; extend `_collect`'s namespace adapter for those exact files only. Snapshot/manifest creation and file/parent barriers precede journal/resource authority changes. A private SQLite snapshot is recovery evidence, never restored automatically over Core. ## 3. Explicit plan binding and crash-resume rules

Do not call B1 `verify_plan` after each mutation and expect its old source digest to match. Its exact self-only exclusion is correct for read-only planning and must remain correct.

1. Install optional B2 schema *before* computing a new B2 plan. Capture the complete bounded logical schema/data/inventory/journal/marker projection, including **all** prior B1/B2 plans, resolutions and certificates. Only the current B2 plan's own row and its exact duplicate typed-reference labels are excluded during immediate self-verification. Plans appended later stale earlier unapplied plans. No blanket `p1_*`/history exclusion.
2. Initial apply checks expiry, complete source digest, exact affected set, all older history, scope/configuration and fresh host proof **before** accepting any authority transition. Save immutable prestate, plan digest, proof digest and preselected new lane/epoch. If a matching receipt-side pending intent exists but the Core intent is absent, resume only that exact intent/prestate; do not create a new random recovery ID/lane.
3. Once accepted durably, expiry does not strand maintenance halfway. Same-plan resume after TTL is permitted only for the existing accepted recovery, never for changed policy/set/budget/proof. Revalidate death/no live or unknown consumers and both locks on each invocation. If an incarnation restarted or the daemon/volumes changed, stop; do not casually substitute a fresh proof into the accepted record.
4. Each of the few named steps has a persisted expected input and deterministic output. Compare the current state to the exact before/after states for that step, including unaffected rows/history and media identities. A durable output with an absent step receipt is verified and re-recorded idempotently; it is not recreated. Wrong archive bytes, another lane, extra history/plan, modified prior plan or unexpected row/media changes refuse. Logical projections avoid physical WAL churn; the separately bounded evidence snapshot still preserves physical source content.
5. Never exclude whole resolution/recovery tables or journal/inventory from resume checking. Validate the current recovery's own appended records against its step chain and before/after projection, then bind them explicitly. Account for its exact new typed-reference labels and archive entries. New integrity observations and budget changes must be predeclared step outputs, not treated as invisible drift. Fingerprints exclude their own digest fields when computing a certificate; no self-hashing fixed-point requirement.
6. Core completion is one atomic transaction: action outcomes, resolutions, retired publications, retained reservations, monotonic high-water, archived fault/monitor history, new resource epoch attestation and completion certificate. Failed/ambiguous COMMIT requires close/reopen and inspection; no live retry assuming rollback. Receipt finalization follows only a verified durable Core completion. Same completed apply returns the existing certificate, creates no lane/epoch/events/resolutions and does not run another ordinary scan. Later registration/ordinary activity does not make a completed apply replay old mutations: validate its immutable completion chain and return an already-complete result, while reporting current startup eligibility separately.

## 4. Authority, outcomes, and the exact reconciliation amendment

Union **all retained registrations**, not merely the latest registration passed to `Docker.observe`; current `check_consumers` already reasons over history but the host wrapper accepts only one registration. Actual-host evidence is accepted only through the trusted host-admin transport; `E1-mock` exercises internal validators in tests but must not be accepted by shipped apply. A digest/string labelled actual-host is not authentication.

B2 implements the closed request/proof validators and fixed host operations; C1 owns actual maintenance container/image/mount packaging, C2 proves it installed. Do not weaken provenance to make a local CLI demonstration work. No runtime Docker socket or service-imported host observer.

Recovery planning needs a narrowly separate journal observation mode. Current B1 snapshot requires a present, parseable, digest-valid journal; blindly reusing it cannot recover missing/corrupt journal. Keep ordinary B1 inspect/plan behavior unchanged. B2 can record `valid`, `missing` or bounded `unreadable` journal bytes/status, but may proceed only with coherent control/reservation authority and exact registration/container coverage of **every possible owner**. Missing bytes are not an empty journal. Preserve corrupt bytes; for absence preserve its observation and prior known lane/registration evidence. Symlink/foreign owner/unbounded content/unknown namespace or ambiguous lane/boot coverage refuses. No inference of clean receipts from corruption. Valid old journal may contain UNKNOWN old-boot rows or be clean/full; both require the same freeze/proof/archive path. Fresh lane/UID namespace is chosen once; old lane/runtime IDs never become valid again.

Nonterminal affected work closes unsuccessfully after proof. Queued jobs follow cancel-request/never-started semantics; running work fails, previously cancel-requested work cancels. Existing terminal job JSON, attempts, events, artifact/reference rows and idempotency history stay unchanged. For nonterminal attempts, a `reaped` transition may reflect proven tree death but never a fabricated PID-1 receipt/timeliness/ACK; the separate operator evidence remains the reason. Preserve all original dispatch/command/receipt/outcome/acked fields. DispatchStore.current excludes only resolutions whose owning recovery has a valid Core completion; pending rows never hide a dispatch. Both replacement entry and allocation reject operator-resolved jobs, including resolved jobs without a publication. A separately requested retry job may retain ordinary lineage.

Resource recovery sets only proved executing/queued reservations to retained; demand JSON/disk charges never decrease. `highwater=max(old, bounded_actual)`; archive old monitor/faults before clearing active faults. A fresh recovery scan under durable pending authority can establish the **new** epoch, never complete inherited checking via `observe`. Over-budget/free-reserve failure stays pending/blocked without partial healthy state. An explicit finite disk-budget increase must be planned before acceptance, recorded old/new, validated against capacity, and consumed as an effective configuration from completed history; original enrollment record remains immutable. No automatic increase, queue/execution-budget redesign or credits for deletion. Replanning before acceptance is allowed; after acceptance a changed budget requires a separate reviewed recovery decision, not overwriting the plan.

**Root amendment required beyond the already approved reconciliation adapter:** allow `service/reconciliation.py` to (a) recognize exact completed dispatch/publication/diagnostic resolutions in `_collect`'s owner/reservation/receipt joins and (b) consult those exact diagnostic resolutions when deciding whether historical defects remain unacknowledged in `reconcile_startup`. Without this, retained reservation + unchanged absent outcome/receipt still produces `reservation_outcome_mismatch`/`terminal_receipt_missing`, and historical object defects relatch forever. Limit the amendment to validated complete recovery ID + exact original tuple/reason/content digest. A changed/new defect is unresolved. Pending records have no effect. Preserve typed references, raw history and availability reports. Do not delete publications/history or invent receipt/outcome to satisfy A2.

The recovery writer in `service/recovery.py` may explicitly settle an inherited A2 `checking`/`unresolved` state as part of the proof-bound new recovery epoch and recorded diagnostic decisions after a complete bounded scan. It must archive old state/token and never borrow the ordinary `_begin` token. **Ordinary** `_begin/reconcile_startup` and R1 observe retain their existing inherited-checking refusal when no valid completed recovery accounts for it. Missing terminal media remains unavailable and strict retrieval fails even when explicitly accepted as degraded. Unknown references/schema, missing reservation origin or incoherent authority cannot be acknowledged away. B2 does not grant cleanup eligibility.
