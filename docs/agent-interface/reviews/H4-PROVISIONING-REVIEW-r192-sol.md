## Blocking findings

1. **P1 — retry bypasses failed directory sealing.** `service/provisioning.py:119-124` seals files, renames staging into bundles, then chmods the bundle directory. If that last chmod raises, the old active pointer is preserved, but a writable bundle directory has already been published. The existing-bundle branch at lines 90-95 verifies bytes/manifest/names only; retry skips chmod and activates it at lines 125-138. This needs no hostile filesystem mutation or privileged permission reversal. In an inert fixture, patching only the final bundle-directory chmod to raise produced `first: inert seal failure`, directory mode `0o755`; ordinary retry succeeded, created active.json, and left mode `0o755`. The owner can replace/unlink the nominally read-only files through that writable directory, so even the stated ordinary accidental-write protection is absent. Require verified/recovered sealing before every activation, including existing bundles, and cover failures during the sealing transition. Also consider interruption after only some staging files become read-only: resume rewrites manifest at lines 114-117 without restoring a writable staging state. The latter was source-inspected, not separately executed.

2. **P2 — expected byte pins do not bound acquisition or waiting.** `service/provisioning.py:50-55` reads and writes until remote EOF; expected bytes are checked only after the entire downloader returns at lines 110-112. A wrong/never-ending upstream response can consume arbitrary storage despite a five-byte expected pin, while retaining the global exclusive lock. The 120-second urlopen timeout is not a total transfer deadline; the blocking flock at line 88 also has no wait budget. One-MiB chunks bound buffer size, not total disk, transfer time or lock wait. An inert mocked urlopen source returned 100 bytes and download stored all 100 (fixture model expectation is five); no network was used. Carry the expected size into managed acquisition, stop after expected bytes plus a bounded overflow probe, and define finite transfer/lock behavior or an explicit bounded cancellation contract. Retaining the old active pointer on ENOSPC is useful but does not substitute for acquisition bounds. Existing tests inject ENOSPC; they do not establish this bound.

## Filesystem, identity and compatibility assessment

The closed managed manifest checks exact keys, two fixed asset names, positive integer sizes, lowercase SHA256, explicit origin/revision/license/access and exact runtime package mapping before acquisition (`provisioning.py:22-47,72-74`). Offline operator-supplied expected pins are valid authority for this seam; there is no need to invent public checksums. Origins/revisions are operator assertions, not cryptographically proven upstream provenance. Schema version accepts Python `True` through equality with 1, and malformed types can raise TypeError rather than ValueError; these are input-validation rough edges, not an observed authority bypass. CLI reads JSON and queries package metadata before managed validation (`scripts/provision-tts.py:88-92`); it should not be exposed as public JSON authority.

Managed root ancestors, staging entries and activation symlinks are checked; allowed staging entries are closed, completed assets are rehashed, corrupt completed staging is reacquired, partials restart, and existing bundles are reverified. The flock serializes cooperating provision calls, and its descriptor closes on exceptions after lock acquisition. No test established competing-process serialization. Lock acquisition itself occurs before the try/finally, so a flock exception also leaks the open descriptor (`provisioning.py:87-89,139-140`).

Private operator-owned storage is a documented prerequisite, not enforced: `_directory` creates using ambient umask and accepts pre-existing ownership/modes. Hardlinks are not refused for staging files, manifests, bundles or lock files (no owner/link-count/regular-file fstat policy). In particular a pre-existing verified hardlinked staging asset is reused and chmod at line 122 affects its other link; a FIFO lock path can block os.open. These are reasons to enforce/document provisioning-root admission and exclude pre-populated unsafe storage; this review does not relabel the advertised private-storage/ordinary-readonly design as hostile-filesystem defense. There are check/use races and no dirfd/no-follow traversal throughout. No hostile concurrent filesystem guarantee is established or claimed. Shared `verified_bundle` reads manifest JSON without a size ceiling (`assets.py:22`); this is another trusted-local-storage resource assumption.

Pointer replacement is atomic for ordinary exceptions before replacement, and the supplied activation-failure test preserves the old pointer and bundle. Retrying failed pointer replacement works. No old bundle cleanup exists. Power-loss durability is explicitly disclaimed by r190, appropriately: directory entries are not fsynced. This review does not equate exception atomicity with crash/power-loss durability. The sealing finding above is an ordinary exception/retry defect within the advertised scope.

Legacy Pocket CLI options, config localization, manifest fields and historical manifests without byte counts remain present; shared validation adds size/path/symlink checks without requiring new fields. The focused legacy fixture passes. No actual Pocket package acquisition or CLI network journey was run, so this is source/fixture compatibility evidence only. Discovery/generation were not changed to download; network acquisition remains an explicit script/operator operation.

`readiness_matches` (`provisioning.py:144-151`) binds full expected-manifest identity, runtime mapping and profile hash and refuses the synthetic label. It is only a pure predicate over trusted caller assertions: any trusted caller can construct an `actual` dictionary; it neither performs real qualification nor persists invalidation nor checks current bundle bytes. r190 clearly states that limitation. Parent must retain trusted qualification provenance and current bundle/runtime/profile verification at integration. No actual-ready claim follows from these tests.

## Directly proven r189 integration incompatibility — parent-owned adapter

At r189 `worker/engines/kokoro.py:25-33`, execution hashes the actual manifest.json bytes and requires top-level `revision`. r190 `validate_expected` at lines 24-25 forbids a top-level revision; only per-file revision is accepted. Consequently every r190 managed manifest lacks the revision that r189 requires. In addition, r190 `identity` hashes compact canonical JSON (`provisioning.py:18-19`) while manifest writing uses default-spaced sorted JSON plus newline (line 117); active.json labels that canonical-object digest `manifest_sha256` (line 134). That value is not r189's raw-file digest. Direct use of the pointer's digest fails r189's hash check, and computing the raw hash still leaves revision mismatch. This is independently established from both pinned sources, not a request to modify the engine lane. Parent owns the eventual shared manifest/descriptor adapter and must define both revision semantics and digest semantics explicitly before real integration.
