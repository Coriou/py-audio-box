## Reliability assessment

### Transactions, identities and cancellation

`service/core.py:96-115,123-141` establishes WAL/FULL, foreign keys, versioned initialization and explicit immediate transactions. `:168-179` reads the latest revision and inserts the next snapshot within that transaction. This prevents a stale revision from overwriting a newer snapshot under the stated single-control-owner model. Exact text, old snapshots and media identities survive. `tests/service/test_core.py:54-64` covers sequential stale CAS, not simultaneous independent clients. SQLite's default thread affinity is material: callers must queue commands onto the owner, not share this connection among transport threads.

`core.py:181-212` durably scopes deduplication to principal/operation/key and persists context separately from caller objects. Duplicate lookup precedes frozen-plan revalidation; the current API still needs a context to obtain the request and does not itself implement a request-first trusted resolver. F2 at `:201-205` now compares canonical complete contexts and both stored/submitted plan hashes. Tests at `test_core.py:273-301` exercise the meaningful integer/float preimage difference and an inconsistent stored hash. Explicit retries retain lineage and use a distinct job; there is no automatic inference replay.

`core.py:246-281` separates cancellation request from terminal cancellation. `finish(cancel=True)` requests termination, waits for observer-confirmed reap, and allows a verified timely result to win. A queued cancellation needs no worker; reconciliation marks it never-started. **`request_cancel()` alone does not signal the process**; a future dispatcher must service that durable request promptly. Current tests demonstrate serialized cancellation/result paths, not an independently responsive control loop while `finish()` blocks. Do not advertise multithreaded cancellation or transport responsiveness from these tests.

### Deadlines, lost observation and owner handoff

F1 at `core.py:42-74,224-238,260-274` is functionally sound for the known child: observation starts before execute transfer, uses a monotonic cutoff and fails at equality or later; collection joins the observer before publication. Late collection does not invalidate already established timely evidence. Failure to confirm reap raises before active ownership is cleared. Conservative scheduler delay may reject an actual earlier exit; it cannot manufacture earlier evidence.

`test_core.py:230-270,328-344` includes real delayed/late subprocess cases plus deterministic cutoff edges. The lost-observation test at `:304-325` correctly fails interrupted work after control death when there is no durable verified publication intent. A staged WAV alone is not authority. Wall-clock movement between deadline creation and monotonic anchoring is not independently covered; start should eventually derive its runtime budget from one monotonic origin, with persisted wall time for cross-process policy only.

`core.py:217-239` commits a running attempt before acquiring its owner lock and spawning. Conceptually: death before spawn leaves no child and can fail interrupted; death after spawn leaves the inherited lock fencing the known child; death before complete command transfer gives that child EOF when control descriptors disappear (`worker/synthetic.py:23-30`). After dispatch the fixed child's bounded sleep eventually ends and its send fails if control died. **Control death removes its deadline observer**, so the persisted deadline is not enforced by that observer across restart. The current worker may remain alive until its fixed delay ends; the replacement controller quarantines, rather than starting overlapping work. This is an explicit limitation of a disposable synthetic harness, and a blocker to claiming restart-safe deadline enforcement for a persistent worker.

The live-owner test (`test_core.py:159-177`) kills control only after `start()` returns. It does not cover each spawn/registration/send/observer-installation failure. Exceptions before/after Popen also lack a unified bounded unwind path. For example, failure to install the completion observer after `self.active` is assigned leaves `finish()` expecting a missing observer (`core.py:233-234,260`). Do not infer general recovery from the ordinary success-path test. These belong in the immediate ownership continuation before a live executor consumes this interface.

`core.py:352-376` treats acquisition of an inherited owner lock as death evidence for this exact script. That is a reasonable narrow premise because it holds the descriptor until exit and starts no descendants. It is **not** independent OS reap confirmation of an arbitrary process tree; reconciliation nevertheless records `reaped=True`. Reusing that inference for a daemon/companion/container would be unsound. The new supervisor must distinguish alive, confirmed stopped/reaped, and unknown, with unknown quarantined. Reconnect to a live owner resumes observation of the same tuple; it must not create another attempt or reset the deadline.

### Publication, adoption and restart

`core.py:285-311` verifies a result against persisted authority and the child-bound socket, checks staged file ownership/type/size, measures actual WAV bytes, and checks the fixed synthetic provenance. The manifest is a proposal. No worker-provided timestamp supplies completion authority.

The sequence at `:313-350` is coherent: verified durable intent, copied/fsynced immutable bytes, no-replace link, directory sync, then one transaction inserting references and success. This is a two-resource protocol, not a joint filesystem/SQLite transaction. Recovery has a useful narrow rule: verified intent plus matching adopted bytes can complete; absent intent cannot reconstruct success from staging. No automatic retry occurs. Repeated recovery of a terminal job does nothing.

The three crash hooks (`test_core.py:132-156`) bracket adoption and commit; they do not cover every syscall. In particular:

- Crash after link but before temporary unlink leaves link count two; recovery refuses it (`core.py:340`). This fails closed and retains an orphan; it does not demonstrate complete orphan reconciliation.
- Crash after unlink but before directory fsync can leave readable adopted bytes. `_commit_publication()` rehashes but does not establish a fresh directory durability barrier before recovered DB success. Process-death tests cannot prove this power-loss case. Persistent publication acceptance must establish the barrier or an equivalent demonstrated filesystem guarantee, including newly created root/directory persistence.
- ENOSPC coverage injects failure at adoption-file open (`test_core.py:117-129`), not partial write, file/directory fsync, SQLite intent/commit/checkpoint or recovery. SQLite operational failures can propagate from reconciliation; availability and subsequent recovery need explicit tests rather than an assumed terminal result.
- An exception during verification/publication clears the reaped child's in-memory lane in `finish()` but skips the trailing reconciliation. The job may remain running until a later `reconcile()`/`start()`. A persistent dispatcher must guarantee that follow-up and expose a bounded failure state.

Recovery trusts the control-only durable intent; it does not revalidate all stored message/plan relations, and `publications.message` is not consumed by `_commit_publication()`. That is acceptable here only with the stated intact, single-writer DB and trusted private call graph. It is not a corrupted-store repair mechanism. No fault probe of stored authority was performed here.

`asset()`/`artifact()` recheck bytes on retrieval (`core.py:378-394`), so deleted or changed media is refused. Reconciliation skips succeeded jobs: it does not repair or report all broken terminal references, and `job()` can still report historical success after external deletion. Keep immutable roots service-owned; persistent startup/integrity policy must make unavailable media explicit without inventing bytes, silently rerunning synthesis or rewriting terminal history.

The accumulated stages, owner files and publication intents are retained. This avoids premature destructive cleanup, but creates an unbounded disk accumulation over repeated jobs. Queue length and the 1 MiB per-result check are not disk admission. Trusted synthetic integration is acceptable; unattended/persistent operation must wait for quotas, free-space reserve and reference-aware reconciliation.
