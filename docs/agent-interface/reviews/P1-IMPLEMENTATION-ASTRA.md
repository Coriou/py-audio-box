## Invariants and private persistence format

One Core lock/owner thread remains the writer. Runtime RPC stays outside SQLite transactions. Startup inventories/reconciles before new dispatch; a storage error retains ownership and diagnostic evidence, with readable metadata where the DB permits it. No partial reservation/job/settings/attempt mutation. Preserve current profile validation, FIFO, independent budgets, replacement disk accumulation, current generation and original deadline. No successful output from an unverified intent, stale generation, unknown owner or unresolved resource epoch.

Keep public contract 1.3.0, Core user_version=1 and R1 resource protocol=2 distinct from a new **private P1 format revision 1**. Add a small private schema initializer in `service/persistence.py` with its own revision row. It owns publication-work records, inventory/integrity observations, deployment identity and recovery/cleanup records in the existing Core DB, not another database. Existing tables and original publication messages remain readable. Each lot adds only its named records transactionally; unsupported partial schemas refuse mutation.

Persistent P1 qualification is **new, explicitly initialized, owned synthetic installations only**. A new installation records a random deployment ID, fixed volume-role identities, profile/budget digest, private format version, and synthetic-only scope. Empty means no preexisting Core DB, journal, keys, marker or unexplained entries, not merely zero jobs. Initialization is create-only with exclusive creation and file/parent-directory barriers. A crash mid-init leaves an incomplete installation requiring explicit completion from its matching initialization record; it must not start a new identity over fragments.

Existing populated pre-P1 roots, revision-1/missing R1 authority, unexplained empty resource tables, historical local attempts and missing reservations stay inspect-only/quarantined. **P1 does not ship migration of those roots.** Preserve them in place; create a separate new named-volume synthetic installation for qualification. Copying old data into a fresh root, stamping a format marker, manufacturing reservations, or rerunning init is not migration. A future upgrade ticket must reconcile that exact old population and explicitly own its migration. This restriction applies to the current root's old test data as well; it is not an excuse to delete it. New-format fixtures must include rejected populated-old-root cases, not only fresh happy paths.

## P1a — publication, inventory and startup recovery

### A1: make the existing publication protocol recoverably durable

Use an additive `publication_work` row keyed by job ID with exact current binding/attempt, destination asset ID, generated temporary basename and byte hash/length. Commit it with the existing verified publication intent **before creating the temporary file**. Paths are derived from validated managed IDs; no caller paths. Keep the current one-output synthetic policy. Old intents without this provenance may be inventoried, but never have a guessed temporary sibling removed.

Ordering for new publication:

1. Existing exact supervisor receipt and healthy R1 publication preflight; validate the original message/manifest/bytes through the existing oracle.
2. Commit intent plus publication-work identity. An ambiguous commit stops the session; reopen and inspect durable state before any next action.
3. Exclusive create of the recorded temporary; bounded complete write, verify full length, flush, file fsync. A short/partial write or fsync error leaves no success.
4. No-replace link to destination. Never overwrite a preexisting mismatching ID.
5. Remove only that recorded temporary alias after validating the relationship; directory fsync. Validate adopted bytes from an O_NOFOLLOW descriptor, file fsync and directory fsync again on **every recovery path before DB success**. Establish parent/root persistence too, including newly created directories and SQLite namespace. Do not claim syncing a file persists its parent name.
6. In one Core transaction insert immutable metadata/references and terminal success. Retry ambiguity by reading committed state, never inserting duplicate events/assets or reopening a terminal job. Receipt/outcome/release/ACK retain their existing ordering.

Recovery cases are explicit:

- **Two-link crash:** recorded temporary and destination are the same regular inode, expected owner/hash/size, exactly two links, both inside the owned assets directory, no other published ID sharing that inode. With exact reap, intact binding and healthy resource authority, unlink only the recorded temporary, sync directory, reverify one-link destination, then commit. This is protocol completion, not general garbage collection; no grace is needed for that exact redundant alias. More links, a different inode, unrecorded alias, symlink or foreign owner means inventory/quarantine, no unlink.
- **Unlink-before-directory-sync crash:** readable adopted bytes are insufficient. Repeat file and directory barriers before committing recovery. Barrier failure leaves intent and references uncommitted.
- **Temporary only / partial temporary / no adopted destination:** retain and classify. P1 chooses failure after exact reap for an incomplete adoption, without replaying synthesis or promoting arbitrary staging. A complete destination plus durable verified intent may recover. Do not add a second reconstruction path that copies from an untrusted orphan.
- **Destination without corresponding intent:** adopted orphan, not success. Inventory and retain; never infer provenance from a WAV/hash alone.
- **Already terminal:** preserve job, attempts, events, idempotency and artifact history. Validate availability separately. No retry-to-success or rewriting succeeded to failed.

Separate media/authority rejection from retryable persistence failure at `_terminal`. I/O and SQLite failures quarantine progress, keep the pending publication and permit a later bounded reconciliation after restart; do not automatically call `_fail` for an fsync failure. A deterministic invalid result can still fail after exact reap. A recovered missing/incomplete adoption can produce the existing failed/cancelled terminal outcome only when ownership/resource authority permits it. A failed storage operation that cannot record diagnostics must remain visible through startup refusal, not require a second writable witness store.

SQLite WAL is part of the durable store. Fault coverage includes intent BEGIN/write/COMMIT, reference/terminal COMMIT, outcome/release transaction, checkpoint and reopened recovery writes. Checkpoint failure is not loss of already committed WAL success: retain WAL/SHM, quarantine writes if health is uncertain, report the failure, reopen and verify. Never delete WAL, demand a successful checkpoint to redefine a prior terminal outcome, or hide a commit ambiguity with retry. Handle rollback-after-failed-COMMIT without masking the original failure or assuming rollback succeeded.

### A2: reference-aware inventory, integrity report and bounded startup pass

Add `service/reconciliation.py`, used by Dispatcher startup and the later offline operator command. It inventories the exact control assets/adoption names, internal staging/owners and configured worker staging; it does not traverse arbitrary host or legacy paths. Return bounded pages (20 entries, opaque cursor tied to scan generation), plus compact counts/reasons in internal status. Long scans have finite entry/byte/time budgets; an incomplete scan blocks dispatch and cleanup rather than silently skipping entries. No giant status reservation/media dump is a new public API.

Inventory classes: committed referenced media; pending adoption/known alias; owned synthetic transient; adopted orphan; unknown/foreign namespace; missing/hash-mismatched terminal media; unresolved owner/receipt/reservation. Store first-observed time, last verified identity, owning tuple where known and reason; retain diagnostic history when resolved. Treat hardlinks conservatively in accounting; do not undercount by assuming duplicate filenames are free space.

Reference traversal covers all current Core tables: assets/artifacts, publications/work records, jobs and frozen contexts, every project revision, plus unresolved dispatches/receipts and active cleanup/recovery records. Merely not being the selected take/current revision is never sufficient. Unknown schema/reference kind refuses cleanup. Asset metadata existence is itself a retention obligation; unreferenced adopted assets are report-only in P1.

Missing terminal media reports `unavailable` with asset/job/artifact identifiers through the internal integrity report; `asset`/`artifact` retrieval remains strict. `job` retains historical succeeded. No replacement bytes, terminal rewrite or inference replay. For simplicity a detected integrity defect blocks new dispatch until explicitly accounted for by operator recovery; reads remain available. Recovery may acknowledge a missing-media diagnostic as an ongoing degraded condition, never clear its availability report or make retrieval succeed.

Startup joins dispatch binding, stored receipt, job attempt, publication intent and reservation. Exact ordinary receipt supports ordinary release/ACK only with resolved R1 authority. An unbound intent, journal mismatch, receipt mismatch, missing reservation or unexplained executing charge is quarantined. Never reconstruct budget from a current profile. A terminal job with an executing reservation needs exact receipt or the separate P1b death proof; terminality alone cannot release it. Repeat startup twice to prove idempotent recovery.

## P1b — explicit offline operator recovery, then limited cleanup

### Selected death authority: exact deployment shutdown, not a reset button

Implement a narrow host-admin command `scripts/p1-operator.py` and a packaged `python -m service.recovery` command. The host command is offline, manually invoked by the trusted host administrator. It uses fixed Docker inspect/wait/stop operations and fixed packaged recovery entrypoints with structured arguments. No generic shell/argv proxy, socket mount, daemon credential or host observer inside a service. It is not part of ordinary dispatch and cannot declare timely completion.

The install/start procedure records daemon/context identity, deployment ID, exact named-volume identities/roles, immutable image IDs, full container IDs, and supervisor lane/boot associations **before admitting work**. Compose names, labels and PIDs alone are insufficient. Registration links the authenticated supervisor hello and protected journal lane/boot to the actual container incarnation observed by the host tool. A worker restart changes boot and must be registered before new work. Existing old runtime IDs remain attached to their recorded incarnation. The installed control must require matching registration; this is finite installation metadata, not daemon access from control.

Procedure, with explicit irreversible steps identified:

1. **Inspect/dry-run:** collect bounded status, pending binding/attempt/generation/deadline IDs, R1 monitor/protocol/faults, reservations, publication/inventory state and journal identity/digest. Prepare a recovery plan ID and digest. Stop new admission. No file deletion or authority change.
2. **Freeze the deployment:** administrator stops every registered control writer and worker container for that deployment; stop policy is explicit, restart remains `no`. Inventory all containers mounting any of its exact volumes, not just Compose service names. Unknown consumers, missing registration, another daemon/context, live writers or ambiguous storage identity stop the procedure. Keep stopped containers until proof is durably captured. Take exclusive normal Core/journal locks; failure means wait/quarantine, never remove locks.
3. **Prove termination:** after bounded stop/escalation, Docker wait completes and inspect of each exact registered container reports non-running/non-restarting, zero runtime PID, with matching ID and incarnation/start/finish observations. Under the supported private-PID-namespace topology, trusted runtime teardown is death evidence for that container's execution tree. Bind this to every unresolved runtime lane/boot/nonce or unbound prepare obligation that could have been served by it. A failed wait/inspect, lost container record, foreign boot, daemon reset or unidentified incarnation yields UNKNOWN. A disconnected socket, stale PID, new boot, timeout, readable output or unlocked file never substitutes. Host/daemon administrators are trusted; this is not a proof against a malicious administrator.
4. **Snapshot and plan:** while services remain stopped, retain a consistent SQLite backup including committed WAL content, original protected journal, metadata and diagnostic/inventory manifests. Use bounded files in the recovery area of the owned synthetic volumes. No private source media is read. Snapshot/fsync/space failure aborts before authority changes. Verify source digest again before apply.
5. **Explicit apply:** operator supplies the exact recovery-plan digest, proof digest and named policy below. Apply handles only that frozen deployment/affected set. Local host transport invokes the packaged command through fixed mounts; an arbitrary uploaded JSON file is not proof. Hashes bind reviewed evidence, they do not authenticate its author. Use a host-owned 0600 evidence file with a dedicated one-shot read-only mount unavailable to ordinary control/worker processes. Recheck live daemon/container scope immediately before invoking apply, keep exclusive maintenance ownership and services stopped until completion.
6. **Validate and reopen:** repeat integrity/accounting, check durable completion across both volumes, then boot the worker, register its new exact incarnation, and start control in inspection mode. Only a complete matching recovery and successful ordinary new R1 check can reopen internal synthetic admission. A fresh request/key may be submitted explicitly afterward. No old start/replacement/retry is triggered by recovery.

An existing valid PID-1 receipt can supply exact death evidence without claiming container teardown, but this first offline implementation still freezes all writers before any reset or deletion. The host path covers worker-boot UNKNOWN and unbound prepare; it must not forge a `pid1-waitpid-echild` receipt. Store operator death evidence as a different private evidence kind. Preserve the original receipt, including its absence. Do not falsify `timely`, `reaped_children`, runtime ACK or a terminal job's attempt history.

### Reset policy: close affected work unsuccessfully; open a new resource authority epoch

Use the closed policy name `abandon-uncertain-synthetic-v1`. This is an explicit operator decision to accept loss of uncertain work, **not evidence that an inherited checking scan was healthy**. Supported only on a coherent, enrolled P1 synthetic installation. Corrupt/unreadable DB, unknown reservation origin, old/missing resource protocol or uncertain death stays quarantined; no repair by zeroing tables.

For each exact affected allocation, record an append-only resolution with proof digest, prior monitor/faults/high-water/reservations, original outcome and reason. Nonterminal running work becomes failed, or cancelled if cancellation was already requested, after death proof. Queued jobs in the reset set are explicitly cancelled through the ordinary cancel-request/never-started transition; record that choice in the plan. No outstanding work from the old uncertain epoch is silently carried into execution. Already terminal jobs/events/attempts/artifacts remain byte-for-byte historical; death and resource resolution live beside them. Never publish an uncertain intent after this reset, even if it later appears timely and valid.

Add `dispatch_resolutions` keyed by dispatch seq/recovery ID. `current()` excludes only **completed** resolutions, not pending plans. Keep dispatches, commands, receipt, original outcome and `acked` unchanged when no real ACK occurred. Explicitly retired unresolved intents are retained as diagnostics and excluded from future adoption. The existing replacement path must reject operator-resolved dispatch/jobs; a new explicitly requested retry job preserves normal lineage.

Resource transition is atomic in Core DB with resolution: executing/queued reservations become retained only after their respective exact death/never-started proof; **disk demand and high-water do not shrink in P1**. Archive active fault reasons and prior monitor state into immutable recovery history before removing active fault rows. A recovery-specific, owner-only scan runs while the recovery state is durably pending and cannot allocate/publish/release normally. It checks the complete bounded namespace, finite configured budget/free reserve and actual output/integrity classification. Persist pending before observing. A fresh scan may attest the **new** epoch only after explicit abandonment and proof; it never calls ordinary `observe` to close an inherited token.

If retained high-water plus charges still exceeds budget, remain blocked. The operator may explicitly increase the finite deployment disk budget/free-space allocation within available capacity, with old/new values recorded, then re-plan; no auto increase, decrement or capacity claim. Cleanup alone grants no credits. This intentionally conservative P1 has finite throughput and can still reach R1 disk or journal ceilings. Do not advertise indefinitely unattended operation. Reclaiming historical disk accounting or retiring audit history requires a later explicit accounting design, not a subtract-file-size shortcut here.

For worker UNKNOWN, all affected incarnations must be dead. Preserve the entire old journal durably under a recovery-specific archive, then initialize a fresh journal lane and retain a retired-lane mapping. Never modify unknown records into fabricated terminal receipts. Old runtime IDs stay unusable. A full but clean journal may use the same explicit offline rotation after all outcomes/death are resolved; no automatic eviction or UID reuse within an old lane.

Cross-volume recovery is a small idempotent state machine, not a transaction claim. Persist the Core recovery intent and a protected receipts-volume maintenance fence before altering either authority; both startup paths refuse a pending fence. Each step has input digest, durable output and repeat check. Archive old journal, write fresh lane through Journal's durable save path, commit Core resolutions/new epoch/history, then complete the receipt-side fence. Either partial direction still refuses dispatch until both sides match the same completed recovery ID and lane. Re-entry with the same plan resumes exact steps; changed inputs need a new plan. Worker startup must check the maintenance fence before listening; control checks the matching completion before ordinary reconciliation. Never clear a pending marker in `finally`.

### Initial cleanup policy: only owned unreferenced synthetic attempt data

Add a separate closed policy `synthetic-transients-v1`, **disabled by default**, dry-run first. It may delete only enrolled P1 attempt staging directories/files and recorded abandoned adoption temporaries, whose synthetic ownership, no references and exact reap/death resolution have been proved. Adopted destination assets, all publication evidence, worker journals/archives, DB/WAL, locks, recovery evidence, originals, voices, references, projects and history are excluded. Unclassified files and all legacy roots are excluded. No filename-prefix-only eligibility.

Grace is **24 hours since the later of confirmed termination and first persisted unreferenced inventory observation**, not mtime. A backward/uncertain wall-clock interval defers eligibility; P1's operator clock is trusted, and suspicious discontinuities require a fresh full grace observation. Recheck all references, tuple, inode/owner/type/link-count/hash/size and recovery completion immediately before unlink under exclusive maintenance ownership. No live worker or writer during this first implementation; consequently no new reference or engine write races the apply. Symlinks, unexpected hardlinks, mount crossings or changed candidates reject that candidate and retain it.

Dry-run produces candidate IDs/digest and total count/bytes. Explicit apply binds deployment, inventory generation, exact candidate set, policy, count/byte ceilings and expiry; no wildcard/path input. Default maximum per apply is 100 files and 16 MiB; larger work uses new bounded plans. Log delete intent before unlink, sync containing directory, then record completion. Restart reconciles already-absent exact targets without duplicate credit; uncertainty keeps the intent unresolved. Do not recursively remove an unexpected entry. Empty owned stage removal is separately checked and parent-synced. Cleanup neither resolves an uncertain resource epoch nor releases execution nor reduces charges. This is an automatable bounded deletion procedure invoked explicitly, not a background collector or authorization to clean current user data.
