## Why this option, and the exact contract delta

The earlier accounting report says accepted restart uses the owned document and bundle; K implemented that as an unconditional bundle read. Amend only that sentence's pre-bundle case: **an exact protected receipt acceptance with no creation attempt may reconstruct the fixed original snapshot under the owning bounded session, subject to the predicates below; after any attempt, durable bundle inputs are mandatory.** The lower semantic kernel's historical ability to capture is not itself authorization for the bounded route.

Selected durable order remains:

1. Final committed plan, production-owned snapshot/hash, immutable intent and full preparation validation.
2. Required marker; full accepted receipt document with file and directory barriers.
3. Exact pending fence (or replacement of the validated preceding complete fence), with barriers.
4. Exact bundle creation descriptor with barriers; exact bundle bytes with file and parent barriers.
5. Core accepted intent transaction; pending receipt; evidence; journal; atomic Core completion/certificate; receipt certificate, bound journal, complete fence; fifth SQL receipt.

Receipt pending and the durable exact bundle still precede **Core acceptance**, and evidence barriers still precede journal/resource authority changes. Accepted-file persistence is earlier than fence persistence; do not describe `accepted-parent` as already having the pending fence. On a first recovery the required marker without fence blocks the worker. With a completed predecessor, the old complete fence can still authorize worker boot until replacement; the host freeze remains mandatory throughout. This amendment does not invent a worker-side pre-fence guarantee or let services restart there. A detected intervening incarnation change refuses unfinished continuation even if the owner is stopped again.

Moving staging earlier would require a durable, discoverable owner for a pre-accepted descriptor/bundle and changes to receipt-only successor recognition, previous-complete replay and creation prerequisites. Moving only two writes would produce an unrecorded namespace or require an unsafe wildcard allowance. A new staging record would add more durable states and retention obligations. Exact recapture closes the identified ownership gap without those changes, using the original protected DB plus already durable plan/accepted before-image/hash. Its availability limit is explicit: logically equal SQLite with different backup bytes is refused, never rehashed.

**Record/schema/order delta: none.** Keep all versions, SQL tables/columns, closed plan/intent/step fields and filenames. The existing bundle descriptor remains exactly `{revision, recovery_id, intent_digest, source_digest, snapshot_digest}` at `p1-recovery-<id>.bundle.intent.json`; its output remains `p1-recovery-<id>.snapshot.bundle`. No restart ticket, receipt status flag, generic staging directory, second authority database or cleanup protocol.
