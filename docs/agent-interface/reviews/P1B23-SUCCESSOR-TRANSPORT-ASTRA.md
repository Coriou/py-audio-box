## Actual conflict and growth mechanism

In owning recovery.py, `_prepare_abandon_locked` constructs the final committed plan and actual snapshot, derives and validates the canonical intent, then checks `encode({"result": result})` against 65,536 **before rehearsal**. `_run_bounded_maintenance` independently checks the same ceiling after the operation and reads at most 65,537 bytes. The receipt certificate includes four step outputs, including Core output rows, and keeps its separate 64 KiB limit. The full preparation result additionally embeds the complete before/source/history.

`snapshot` retains all prior plans, recoveries, steps, resolutions, references and inventory; only the exact current proposal/prefix exclusions apply. `before.source.data.p1_recoveries` contains prior canonical record **strings**; each prior record itself contains its older source. Successive JSON encodings escape those strings again. Source also retains prior step outputs and plans; current intent duplicates selected Core rows/actions for the prescribed after-image. Thus growth is neither a fixed number of bytes per generation nor bounded by one certificate size. Recursive duplication and escaping can accelerate growth even with one retained dispatch. JSON character count is not UTF-8 byte count. No fixed multiplier or number of supported recoveries can be inferred from the two B measurements.

`_validate_b2_database` checks actual SQL population/bytes before decoding, complete historical resolution sets and exact old-row inclusion, then archive populations. `_validate_source` and snapshot add their own encoded/reference/population bounds. ## Selected envelope and bound composition

Define a new internal constant in recovery.py, `MAINTENANCE_RESULT_LIMIT = 1_048_576`. Its numeric value matches existing snapshot/host-document limits but it is a distinct constraint, not an alias that silently changes with another policy. No request, environment, plan field or caller-provided numeric limit selects it. Keep the existing on-wire outer envelope `{"result": result}`; its **entire canonical UTF-8 encoding** must be at most this limit, inclusive. No compression, chunked multi-frame history, spill file or reference lookup is introduced.

Preparation still returns exactly `{plan, plan_digest, intent, intent_digest}`, with full original documents, not IDs substituted for documents. Keep `_Preparation` and `_PreparedSnapshot` as the existing internal owned handoff. Validate the full result size before rehearsal/return/confirmation and before any receipt acceptance, irrespective of whether the consumer stays in the child. The outer encoder/reader enforces the same maximum independently. Small completion/control outputs remain subject to their existing semantic/document limits; the larger channel does not enlarge a receipt or authorize a new result shape.

The relevant constraints are simultaneous:

| Constraint | Selected treatment |
| --- | --- |
| Preparation transport | Whole canonical `{"result": four_fields}` ≤1,048,576 bytes, checked in locked preparation and at child boundary |
| C proposal stdout | Same four fields plus one LF; bounded by the same 1 MiB ceiling; outer wrapper is 11 bytes versus LF's 1, so a passing preparation envelope fits this line |
| Host capsule and C `host_json` parser | Existing 1 MiB limit unchanged; an intent inside a passing preparation frame is smaller than this limit |
| Snapshot | Actual committed original backup ≤1 MiB; no recapture to change its hash |
| Manifest, control certificate, receipt certificate | Each ≤65,536 bytes; no increase |
| Mutable DB/WAL/SHM and every newly written file | Existing 4,194,304-byte hard file-length envelope; all connections/copies/close/checkpoint remain inside it |
| Logical/source/archive/receipt populations | Existing 2,048-entry and 16 MiB checks, deadlines and namespace rules, at their actual call sites; no pooling unused capacity between limits |
| Footprint and quota | `U_all_early = M + 3*4_194_304 + 1_048_576 + 2*65_536 <= H`; `H + charges <= budget`; existing free reserve and final `max(actual,H)==H` |

The transport is a pipe, not a new control-root file. No term is added to or removed from the H formula: M already includes retained control archives and SQLite lengths; the existing three-file absolute term covers current SQL growth, and current snapshot/manifest/certificate allowances remain unchanged. Receipts remain outside that measured-root formula but inside their independent namespace/byte/free-space obligations. `_rehearse_preparation` currently reserves `used + len(snapshot) + sum(document lengths) + 18*65536 <= 16 MiB` and `count + 18 <= 2048`; retain that conservative reserve, including the actual larger intent. Demand charges, budget and retained H do not shrink. Copying old evidence remains bounded per file.

**1 MiB is sufficient to remove the identified transport contradiction, not a completion proof.** A result below it may fail snapshot admission, 64 KiB receipt output, aggregate history, a deadline, or concrete DB/WAL/SHM rehearsal under 4 MiB. Rehearsal starts from the actual physical original DB/WAL/SHM copy, not only the normalized snapshot. Keep that distinction. Do not catch capacity failure and raise a cap, retry live, erase a failed plan, or rehash a new snapshot. A late refusal can retain the already committed unaccepted plan/schema; early known envelope/quota/source refusals still precede those writes. No accepted document/fence/bundle/Core recovery or healthy epoch may be added by a preparation-capacity refusal.

This amendment does not retrofit a stricter transport limit onto previously accepted durable histories. Owned restart uses the existing accepted-document/file/parser limits and semantic validators; it does not re-emit a preparation frame or rerun initial admission. Genuine completed replay must remain observational even where new preparation is now impossible.

## Closed transport and memory contract

Implement one small shared canonical result encoder/checker and a strict result-frame decoder in recovery.py; no new transport module/framework. Use the existing `encode` settings: UTF-8, `ensure_ascii=False`, sorted keys, compact separators, finite numbers. The only outer key is `result`. Reject duplicate keys, nonfinite values, invalid UTF-8, wrong outer type/keys, extra JSON/trailing bytes and noncanonical bytes. For preparation, require exactly the four fields, their types, canonical plan/intent validators, matching digests and full plan-intent bindings. Content validation is necessary; decoded result JSON never supplies snapshot ownership or restart authority. Preserve the private K operation seam's existing test-only return values; do not weaken production preparation/completion validation to accommodate those tests.

No new wire discriminant is needed: the internal production entrypoint determines whether it expects preparation or a kernel/completion result. Kernel/C completion outputs keep their closed existing status-specific fields and certificate bindings; C additionally has its two existing startup/freeze fields. Do not accept an arbitrary caller-selected schema or a Python object/reference in the channel. Validate at both ends where preparation crosses the process boundary. The returned public value remains the original result, not the wrapper.

Bound the **encoded result buffer**, not merely the final write. Use incremental canonical encoding/counting that stops before accumulating over T, or a bounded counting pass followed by one bounded encoding of the already owned object. Preserve byte equality with `encode` for Unicode, escaped quotes/backslashes and nested retained strings. JSON encoder chunks can themselves contain a whole large string: inspect/count them in bounded UTF-8 slices rather than creating another unbounded byte buffer. Do not build a list of all chunks or repeatedly concatenate whole prefixes. Existing source object/validator allocations are still bounded by their prior population/byte rules; they are not made into a 1 MiB RSS guarantee by this change. Keep at most one accumulated frame per endpoint and a small fixed I/O chunk (≤64 KiB), plus the receiver's single overflow byte; avoid persistent duplicate serialization on `_Preparation`. Release temporary serialization before rehearsal where possible. Parse only after bounded receipt and successful child termination. Memory/Recursion/encoding errors are refusal, not fallback.

There is no current `RLIMIT_AS`/hard RSS result-memory guarantee in the inspected route. `RLIMIT_FSIZE` bounds regular files, **not pipe bytes or Python heap**. Report the new finite transport-buffer allowance and bounded source parsing separately; do not claim total RSS≤T or add an unqualified process memory limit in this lot. No compressed payload that can expand beyond the existing validation bounds is allowed.

Parent read loop: absolute existing 30-second operation deadline includes read, EOF **and child exit**, with bounded reads of `min(64KiB, T+1-used)`. Accept exactly T only after EOF and successful normal exit; T+1 refuses before JSON decoding. Full-looking JSON without EOF is not success. EOF without bytes, partial JSON, premature child death, signal/nonzero exit, short/error write, duplicated frame, extra byte or timeout is not success. Existing child `except BaseException: exit(74)` is adequate as a sanitized failure status; no traceback/source/intent is sent as a substitute result. Preserve deterministic bounded error codes in the parent.

Fix the current post-EOF blocking `waitpid(pid,0)`: use `WNOHANG` with remaining-deadline checks and bounded waiting, then kill/reap the exact owned child on expiry/failure. Close both pipe ends correctly after fork and all parent descriptors on every exit, including fork failure; handle EINTR without resetting the deadline. A full valid frame followed by nonzero exit still fails. If a final result is lost after actual durable completion, return no success/freeze release; a fresh owned inspection determines state. Never infer rollback from transport failure, auto-repeat the operation, or restart services in cleanup.

C stdout proposal writing must be bounded to the same deadline, including backpressure/partial writes; the parent's supervised-child timeout must stay effective. Keep confirmation stdin at its existing 65,536-byte/10-second bound and its closed seven-key identity request. Do not raise it to transport full intent back. A caller that observes only partial proposal bytes cannot authorize acceptance. No newline or flush shortcut is evidence of completion. The C tests must read the proposal incrementally with a finite bound; no unbounded `readline`/`communicate` path may become the purported transport proof.

## Why no compact-reference protocol in this correction

The same-process optimization already exists: `_Preparation` holds the owned `_PreparedSnapshot`; C uses that exact object under both locks. Initial continuation validates session/type/object identity, plan identity and snapshot hash and consumes it once. It does not need a second snapshot transfer. Removing only its result-size check would silently give this route a different admitted history population from preparation-only transport and would leave C's stdout check in place.

A new durable reference would need protected storage, namespaces, capacity charges, preaccept crash ownership, stale/expiry handling and replay rules. A digest is not a retrievable preimage, a caller-supplied path is not an owned archive, and caller RAM is not restart authority. A session handle sent over JSON dies with the child and cannot stand in for a durable bundle. Those changes are larger than this identified problem and are not selected.

Keep full preparation documents on the private operator exchange and compact **confirmation** (IDs/digests only). Routine agent discovery/receipts/status must not inherit this larger payload. This report does not claim a token reduction for administrative preparation. A future explicitly scoped operator adapter may show a summary while retaining the full bounded exchange internally; changing C to emit only identity fields would amend its current four-field proposal contract and needs its own client/authorization review. It is not needed to close this blocker and is not silently authorized here.
