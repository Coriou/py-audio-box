## Source findings and causal limits

**L1 — private startup readers do not own connection closure (confirmed source defect).** `service/recovery.py:944` (`enrollment_gate`) and `:1030` (`startup_read`) use `with private_database(...), sqlite3.connect(...) as db`. Connection context exit handles transactions, not close. The private directory's final source check and temporary-directory removal therefore execute while `db` remains open in the local frame. Exceptions can retain that frame through a traceback/Future; ordinary reference dropping also offers no explicit close-order guarantee. These are private-copy handles, so their late close alone does **not** explain deletion of the original SHM. Correct ownership is explicit close before private namespace teardown on success, early return and exception, preserving transaction semantics where needed. [CPython sqlite3 context-manager documentation](https://docs.python.org/3.14/library/sqlite3.html#how-to-use-the-connection-context-manager).

**L2 — Dispatcher publishes failed initialization before Core cleanup (confirmed ordering defect; V3 mechanism candidate).** `service/dispatcher.py:123` calls `self.initialized.set_exception(exc)` before `finally` shuts down the pool and closes Core at `:126–127`. Constructor `:35` waits only on that Future, not thread termination. Thus the caller can catch the exception and construct its next Dispatcher while the previous thread is still closing the original database. The next `_run` calls `startup_read` before acquiring Core's control lock. Neither startup reader itself acquires the external lock promised by `private_database`'s docstring. Repeated startup tests exercise exactly this caller pattern.

Fresh deterministic control-flow witness: extract the unmodified `_run` AST from root, provide a fake Core and an Admission that raises a synthetic startup failure, and observe the Future's callback. Actual output was `['failure_published_while_core_open=True', 'core_closed']`, exit 0. This proves publication-before-close without timing luck; it is **not** an actual SQLite race reproduction or V3 causal clearance. A last SQLite connection can checkpoint and delete WAL/SHM during close, making this a concrete interleaving to test with two explicit barriers, not a speculative appeal to GC. [SQLite WAL lifecycle](https://sqlite.org/wal.html#avoiding_excessively_large_wal_files).

**L3 — Core construction can fail after acquiring native resources without closing them (confirmed source exception-path gap).** `service/core.py:114–139` opens SQLite and performs PRAGMAs/version/schema/persistence checks with no encompassing cleanup. `persistence.initialize` immediately calls `check_recovery_open`; an incomplete B2 recovery can raise there. Some special branches close explicitly, but not arbitrary failures. `active` is assigned only later; calling normal `Core.close()` on an incomplete instance is not a sufficient generic fix. In Dispatcher, `core=self.core=Core(...)` never assigns either target when construction raises, so `finally: if core` cannot close the partial instance. Direct expected-refusal Core constructions in the half-state test likewise have no returned object to close. A retained traceback can prolong original connection lifetime and later checkpoint/SHM deletion. Exact GC timing and involvement in V3 are unproven.

**L4 — fixture transaction contexts are real hazards, but not a demonstrated explanation of the strict sequence.** Examples `tests/service/test_recovery.py:126`, `:165` use transaction-only connections followed by more recovery work. Such handles can remain live past the `with`, or survive function return through native/Python cycles or traceback references. SQLite explicitly prohibits using **or closing** a parent-opened connection in a fork child; child GC finalization is therefore a meaningful mechanism to measure. Do not attempt to repair it by closing inherited SQLite connections in an at-fork callback. Close owning handles in the parent before the fork boundary. [SQLite fork warning, §2.7](https://sqlite.org/howtocorrupt.html#_carrying_an_open_database_connection_across_a_fork_).

However, immediate strict-family setup is materially better: initialization closes Core (`persistent_init.py:192`); `_lotp_population` closes Core in `finally`; `_kpre_predecessor` and damage/logical readers use `closing(...)`; host state uses owning offline inspection. Sol's connection inventory must establish creation PID/site, explicit closure and remaining liveness without keeping objects alive merely to observe them.
