# Deployed lifecycle — targeted Astra architecture decision

2026-10-16. Source-only review of integrated HEAD `92fb5c9b54f6b1c709eef7327517076718cb4ea3`, which contains W2b `71eec93`. Contracts/fixtures 1.3.0. **GO for the architecture and W2c assignment below; NO-GO for claiming deployed lifecycle implemented, full W2 accepted, production activation or Phase 1A complete.** Final global Astra is separate.

## Decision

Ship a **static Compose worker container with a lightweight trusted supervisor as PID 1**, controlling a separate engine child and its descendants. Control uses private authenticated UDS operations to that supervisor. Docker starts/stops the static services; the application does not create containers. No Docker socket, daemon credential, host runtime broker or host ML installation is required by the running control or worker.

Use the existing container-private PID/network/mount namespaces as the outer execution boundary. Each attempt initially receives a fresh child/process group and private staging directory. **Do not describe a process group as a new PID or mount namespace.** A nested per-attempt namespace would require additional Linux privilege/runtime machinery and is not selected. The container namespace is destroyed on container termination; it is not recreated for each successful attempt. The supervisor can serve successive attempts after exact descendant reap. This is sufficient for trusted self-hosted, packaged engines; it is not a hostile-plugin sandbox.

Select this over a Docker-access companion because container creation is unnecessary for a fixed worker profile. A companion would introduce daemon authority, another privileged service, durable container-incarnation recovery and another installation/failure surface just to manage work the worker's parent can manage directly. An allowlisted broker could keep the socket out of control, but would **still change the canonical no-Docker-socket baseline** and would need an explicit contract/security decision. No such change is authorized by this decision. Do not promote `DockerHarnessRuntime` into production or expose a generic Docker/argv proxy.

The static worker image/profile is selected at installation/configuration time. CPU first; CUDA uses a separately qualified image/device configuration of the same topology. GPU presence does not bypass ownership, quotas or qualification. Native Metal later implements the same logical lifecycle operations through a packaged native supervisor, with its own OS termination and transport evidence. It cannot inherit Linux namespace or `SO_PEERCRED` claims.

## Supported topology and trust boundary

1. **Control/UI container:** network-facing service, ML-free; exclusive writer of service DB, owner store and publication roots. Only it allocates attempts, verifies media, adopts files and chooses terminal job state. It mounts private IPC, staging and required data; never the Docker socket. Runtime I/O must not block the API/event loop or hold a SQLite transaction while waiting.
2. **Static worker container:** `network_mode: none`, private PID namespace, read-only root, bounded CPU/memory/PIDs/tmpfs, `restart: "no"` initially. Exec-form entrypoint runs the supervisor as PID 1; no shell or `init:true` silently changes its reaping authority. The supervisor imports no engine or service DB code. It listens on a management UDS and the accepted execution/result UDS, caches proposals and owns the deadline/reaping loop.
3. **Engine child:** fixed allowlisted internal entrypoint, never client argv. Separate unprivileged UID, no supplementary privileged groups, no capabilities, no-new-privileges; close all inherited descriptors except explicit internal channels. It receives frozen input, allowed read-only assets/bundles and its staging location, but not the supervisor's lifecycle/session capability or receipt directory. No application/API/cloud credential is mounted anywhere in the worker. The private IPC capability is narrowly scoped execution authority, as in W1, not an application credential.
4. **Initialization:** bounded one-shot volume ownership setup, as with current Compose, exits before services start. No daemon access. Worker mounts only private IPC, staging, read-only selected input/bundle roots, and supervisor-owned lifecycle receipts. It never mounts service DB, adopted publication roots, control secrets or the entire control data directory.

Use a root supervisor with only the capabilities needed for dropping UID/GID and signalling its child (`SETUID`, `SETGID`, `KILL`); initialization owns filesystem setup. Drop all others, particularly `SYS_ADMIN`, and test the resulting configuration. Child runs capability-free. Root inside this bounded container is a deliberate trusted infrastructure choice, not an engine privilege. W1 expected peer UID changes to the supervisor's configured UID; mutual authentication remains mandatory. Directory permissions must keep lifecycle UDS/session files/receipts inaccessible to the child. Do not trust a UID declaration without permission/descriptor tests.

Network-none does **not** isolate SQLite or publication files if those files share a mount. Mount exclusion supplies that boundary. Within the worker, supervisor and engine share mounts and kernel resources. UID permissions protect supervisor state; per-attempt staging permissions protect other retained attempts under sequential execution, but there is no general per-attempt mount sandbox. A compromised engine may damage its writable staging or exhaust its container; it must not forge supervisor receipts, signal the supervisor, open the service DB or publish. Host/daemon administrators and the shipped supervisor are trusted. Do not add privileged nesting, seccomp research or a micro-VM to this trusted-self-host lot.

## Exact lifecycle and authority

Define a small separately versioned **private lifecycle protocol**, leaving canonical execute/result/manifest 1.3.0 unchanged. Closed operations: `hello`, `prepare`, `start`, `observe`, `stop`, `collect`, `ack`. No arbitrary command/path, generic signals, container names or client-supplied observation state. Each allocation operation binds the full W1 authority digest and immutable job/attempt/generation/owner/staging/deadline tuple. Management authentication is separate from the engine channel. Reuse bounded framing and nonce/HMAC primitives, with domain-separated lifecycle proofs; do not let an execution capability authorize lifecycle operations accidentally.

Runtime identity is `(installation/lane id, supervisor boot incarnation, allocation nonce)`, not PID or Compose service name. The supervisor creates the incarnation and allocation nonce; the trusted control persists them. Fresh supervisor-generated random IDs prevent conflating starts, but IDs alone are not death proof. The supervisor's direct parent/reaper relationship and protected receipt chain are the evidence authority. This deliberately classifies the supervisor as runtime infrastructure, while the engine remains a result-proposing worker.

Required ordering:

- Control durably commits intent before `prepare`. Supervisor durably reserves the exact tuple and runtime identity before returning it, without spawning. Repeated prepare for that tuple returns the same reservation; conflict is refused.
- Control binds that identity before `start`. Supervisor commits a start fence before any fork/exec. Repeated start/reconnect never spawns again. Crash around that fence without terminal proof is unknown, not safe-to-retry. Failed exec can be proved stopped only by the same supervisor's actual wait/reap.
- Supervisor captures one monotonic deadline budget from the original absolute deadline before start and installs enforcement before launch. Expired allocation cannot start. Neither reconnect, replay, cancel nor control restart can extend it. A boot change cannot reconstruct a running allocation by recalculating a budget. Wall-clock changes after anchoring do not change the cutoff; pre-anchor discontinuity remains a qualification limit, not a real-time guarantee.
- Deadline and stop processing are independent of the UDS request handler and child computation. No blocking `receive`, generator call, log pipe or SQLite request may starve the watchdog. TERM, bounded grace, KILL, then wait/reap; deadline enforcement continues with control entirely absent. Uninterruptible processes or an unresponsive supervisor yield unknown; no finite kill guarantee is invented.
- PID 1 adopts orphan descendants. One active execution lane and no unrelated resident child in W2c: stop all execution descendants, drain `waitpid`, and establish no remaining children before STOPPED. Killing only the original process group or waiting only for its leader is insufficient (include double-fork/setsid cases). No launches are allowed during drain. Keep launch handles and boot identity; do not signal reused bare PIDs from a journal. If the chosen Python implementation cannot establish this, W2c is NO-GO, not permission to weaken reap.
- Persist terminal evidence only after OS confirmation, using an atomic file/directory durability protocol in a supervisor-only volume. This is a private lifecycle journal, **not a worker-accessible service database** or a second product job store. Receipt includes identity, tuple binding, outcome/reap evidence and whether complete proposal plus termination were observed before cutoff. Engine timestamps/exit assertions are not evidence.
- `collect` retrieves the cached original proposal and supervisor receipt under a new bounded communication deadline, including after execution expiry. It never runs execute again. No timely result may be inferred just from a WAV or receipt arrival time. In W2c, require both complete proposal and descendant reap before the original cutoff for timely-success evidence; late collection is allowed. Control still verifies bytes/manifest and decides publication. Stop acknowledgement never means cancellation won.
- Retain terminal receipt/proposal until control durably records the outcome and sends bound `ack`. Ack permits receipt retirement under the defined retention rule, not arbitrary staging deletion. Unknown never permits ack/cleanup/replacement. Freeze a small bounded receipt count/size; if unacknowledged receipts fill it, refuse new work rather than evict evidence. Broader disk policy remains R1/P1.

### Restart is a first-class state, not a test-injected observation

**Control dies:** the living supervisor retains child ownership, deadline and original proposal. New control loads OwnerStore, authenticates the same supervisor incarnation and observes/collects the same allocation. No daemon or host helper participates.

**Supervisor/container dies:** there is no in-container observer capable of certifying its own lost final actions. Docker tears down the old container PID namespace, but a new supervisor must not claim it observed that teardown. New boot reads protected journal before accepting work. A durable terminal receipt already written by the old trusted reaper may be replayed for that exact old identity. A prepared/started allocation without terminal proof is **unknown and quarantined**, including an empty/corrupt/missing journal when control still has a bound active allocation. Missing socket, boot change, PID absence and a new lock are not proof. Do not replay start. A second supervisor must refuse a live lane lock; acquiring it only serializes writers, never certifies old death.

**Idle clean restart:** if no unresolved allocation exists and all retained terminal receipts reconcile, a new boot can establish a new lane incarnation. It cannot reset an unresolved control binding. Start/restart policies remain explicit; no automatic container respawn is required for W2c.

There is no additional companion to restart in this topology. Restarting the supervisor is the relevant companion-equivalent failure, covered above. The supported immediate response to uncertain old ownership is visible quarantine. Automatic recovery from such a crash is deliberately not promised. Before unattended activation, P1 must provide the operator recovery procedure: stop/inspect the exact deployment through ordinary host Docker administration, record trusted termination evidence for affected incarnations, then reconcile through control. Deleting a volume, clearing a lock or clicking “retry” is not that procedure. No hidden daemon access in either container may implement it. W2c need not build a Docker recovery broker.

## Contract changes to make deliberately

Compatible without public wire changes: W1 immutable authority and manifest, control-only DB/publication, private UDS, network-none worker, no Docker socket/credentials, unknown quarantine, one conservative CPU lane, explicit profile qualification and future native Metal interface.

Deliberate internal updates for W2c: replace container identity with supervisor/allocation identity for this adapter; classify the supervisor as trusted runtime infrastructure rather than trusting engine testimony; add lifecycle protocol and protected journal; configure supervisor peer UID; define fresh child/process group inside the existing container namespace; add explicit post-deadline collection; preserve stop-before-verification for the synthetic child. OwnerStore layout/history changes beyond adapter compatibility belong to dispatcher integration. Existing Docker harness remains historical/test-only.

Do not silently claim resident-weight reuse from this per-attempt child. **Phase 2B must implement and review a resident execution mode:** long-lived backend owner, serialized commands, separate attempt fence, trusted observed quiescence before staging adoption, and full owner-tree termination on cancel/error/deadline or uncertain quiescence. Current `Supervisor.verify` requires STOPPED; it must be deliberately extended for that qualified mode, not fed a false STOPPED for a resident process. Until then this architecture ships only the fresh-child synthetic mode. Resident reuse remains required by the plan, with its own lifecycle/adapter qualification; it is not removed to simplify W2c. Native ML imports never move into PID 1.

## Remaining order and acceptance gates

1. **W2c** above closes the packaged lifecycle gap. It can be accepted independently now; do not enlarge it into all core integration.
2. **W2d dispatcher/allocator integration:** single serialized control writer allocates unique generation/attempt/staging, persists dispatch and asynchronous runtime commands, reconciles startup before admission, and consumes real supervisor receipts. Replace the active local synthetic path rather than running two authorities. Separate bounded runtime I/O from owner-thread DB commands; reads/cancel/status stay responsive. Exercise queued/running cancellation, timely result winning, expiry, stale proposal, lost ACK and pre-verification interruption through actual core terminal policy. No worker publication. Temporary synthetic-only gate remains explicit.
3. **R1 authoritative admission:** host/deployment heavy-lane reservations shared by inference/decode/render/provision, current qualified profile checks, memory/PID/disk/free-space limits and release only after exact ownership resolution. Static container limits are containment, not host-wide admission or RAM-fit evidence. Reconstruct reservations after restart; coexistence with legacy/external workloads needs declared capacity, not an assertion of exclusive host ownership.
4. **P1 persistent activation:** real persistent volumes, directory/file/SQLite failure and orphan/missing-media reconciliation, receipt/owner/reservation recovery, safe cleanup and explicit operator quarantine recovery. Full installed fault matrix, no power-loss claim from process kills alone. Only then permit unattended persistent synthetic execution through the public dispatcher, subject to remaining product gates.

**Full W2 acceptance waits for W2d** and the original W2 interruption/cancel/result/deadline/replacement matrix on the integrated runtime; W2c GO alone cannot close it. **Activation additionally waits for R1/P1.** Preserve the foundation's subsequent D1 registry → D2 ingest → D3 trusted request-first plans → D4 history/idempotency → D5 render ordering and shared-client gates; no whole-product replan is needed. Phase 2A/2B then integrates real adapters, provisioning and resident mode, followed by separately measured CPU/CUDA/Metal qualification. Required accelerator goals remain open until evidenced or explicitly resolved at release scope.
