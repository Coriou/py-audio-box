# Non-destructive legacy import policy 1.0.0

Service metadata/files live in a **distinct new service root**. Legacy cache, registry, output files and Redis jobs remain authoritative for unchanged legacy commands. There is no bidirectional sync or conversion in place.

1. Produce a read-only inventory/dry-run manifest: original relative identity, exact voice ID/aliases, original JSON/reference/audio/prompt hashes, source schema, supported engine/model metadata, missing provenance, collisions, unsafe serialized content and pending Redis requests. Do not unpickle prompts to inspect them. No private inventory is committed to the repo. Canonical preview hash covers this complete inventory and chosen destination schema/root identity.
2. Preserve IDs/aliases byte-for-byte. Detect collisions across canonical IDs and aliases and against existing service history. Default is stop with `migration_collision`; no force overwrite. Operator may supply an explicit reviewed rename map that preserves old alias if unambiguous. A source hash mismatch invalidates preview/apply. Missing references are blocking for ready voices; missing provenance remains explicit `missing_fields`, never a synthetic assertion of consent, transcript or origin. Unsupported prompt bundles stay legacy-only until a trusted preparation path exists.
3. Apply only from a frozen verified preview with a destination revision precondition and idempotency key, under exclusive control ownership. Create immutable copies (no move/delete/hardlink to mutable legacy files), verify copied hashes, then atomically commit destination metadata. On interruption retain a journal; do not expose partial ready voices. Same manifest can resume without duplicate IDs. Collision or changed source aborts without destination publication.
4. Pending/running legacy jobs remain in Redis and are neither imported nor automatically retried. Report IDs/counts locally with redaction; operator explicitly drains/stops/fences legacy owners if later moving production. New service jobs never dispatch through Redis. Completed outputs may be imported as immutable artifacts only with available provenance; historical success is not re-certified.
5. Before service-schema upgrade: stop admission, drain or explicitly interrupt/fence jobs, consistent DB plus referenced-file backup, retained prior image/schema manifest. Apply versioned migration; verify hashes/readiness/projects/selected takes/exports in the new root. No model activation is implicit.
6. Rollback of initial import deletes/quarantines only unpublished task-owned destination staging. After publication, restore compatible DB+files snapshot into a fresh root; changing image tags alone is insufficient. No automatic reverse migration or deleting newly referenced outputs. Legacy root is unchanged throughout. Test restore before redirecting clients; no real-data migration execution is authorized here.

`migration_report` is the public bounded report shape. Detailed inventories remain local artifacts, not oversized API responses. `contracts.validate.migration` checks distinct roots, collision and pending-job policy; it is not an import/backup implementation. Filesystem containment/symlink safety, source-race checks, journals and fresh-root restore need Phase 2/6 integration tests.
